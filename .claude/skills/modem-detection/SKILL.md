# `modem/` package

Hybrid detection cascade, each tried in order until one finds a modem: **ModemManager → `ubus` (WaveOS's own `qmi` object) → QMI (`qmicli`)/MBIM → `uqmi` → AT-over-serial**. `ubus` is tried before raw QMI/`uqmi` specifically to avoid QMI client-ID exhaustion when running alongside WaveOS's own `uqmi-ubus` daemon (see Known Issues in the root `CLAUDE.md`).

- `Signal{Technology, Role, RSRP, RSRQ, RSSI, SINR}` — `Role` is `"anchor"` or `"scg"`. `GetSignals()` returns one `Signal` per simultaneously active radio leg (EN-DC: LTE anchor + NR secondary, confirmed live on `aaeon`); `GetSignal()` is a convenience wrapper returning just the anchor leg. Only ModemManager and QMI (`qmicli`) can currently report >1 leg.
- `CellInfo{PLMN, OperatorName, RegistrationState, PacketServiceState, TAC, CellID}` — TAC/CellID normalized to **decimal** across backends, except the `ubus` backend, which currently passes Quectel's raw **hex** TAC/CellID straight through unconverted (known bug, not yet fixed — flagged but deferred).
- **A modem with no SIM can still report real RSRP/RSRQ/RSSI/SINR/PLMN/TAC/CellID** by camping on a cell's broadcast system information (physical-layer, unauthenticated) — it just can never complete registration/attach (no IMSI to authenticate with). Confirmed live on `6global`. Don't assume "no SIM" implies "no data."
- `SupportsCellInfo(method)` — only ModemManager/`ubus`/QMI/`uqmi` implement `GetCellInfo`; MBIM/AT don't yet (no real hardware to validate against).

**⚠️ Two real incidents on `dawn6g`, both tied to the one-shot nature of `Detect()` (runs once per process lifetime — see Known Issues) — confirmed live, both fixed in `cmd/modem-exporter`, fix not yet deployed:**
1. **A reboot can win the cascade race onto a worse method, silently, for days.** Confirmed twice: once (2026-11-19 reboot) landing on `uqmi` for ~26 hours (LTE-anchor-only, no NR leg reported at all, since `uqmi`'s backend can't tell multiple simultaneously-active legs apart); once more (2026-11-23 reboot) landing on `QMI` instead of `ubus`, because `ubus list qmi` genuinely returned "not found" 9 seconds after kernel boot (confirmed live) — `uqmi-ubus` just hadn't registered its object yet at the single moment `Detect()` ran. **Fixed**: `cmd/modem-exporter/main.go`'s `maybeUpgradeModems`, on a 5-minute ticker, re-runs the full cascade and swaps to a better-ranked method if the one-shot startup race landed on a worse one — never downgrades, never a partial per-modem swap.
2. **A backend can "find" a modem yet only ever report N/A, and `Detect()` alone would accept that and never retry.** Confirmed live: `ubus`'s `qmi` object can exist (so `DetectUbus` succeeds) moments before its daemon has anything real to report. **Fixed**: `modem.DetectValidated` (alongside, not replacing, `Detect`) additionally calls `GetSignals` on each candidate and rejects one reporting only N/A, falling through to the next method instead of committing to a dead end. `cmd/modem-exporter` uses this; `cmd/modem-tool` still uses plain `Detect` (an interactive CLI doesn't need this retry behavior the same way a long-running service does).

**⚠️ Separately, a real incident where `radio_cell`'s `rsrp`/`rsrq` froze bit-for-bit identical for ~2.5 days on `dawn6g` while still being written as live data every 30s** — confirmed NOT a bug in this repo's own polling code: `modem/qmi.go`'s `getSignalsQMI` runs a genuinely fresh `qmicli --nas-get-signal-info` subprocess on every single poll (verified by reading the code), and a live `AT+QENG="servingcell"` query plus a fresh `ubus call qmi metrics` both independently confirmed the *modem itself* was reporting correct, moving values the whole time. The likely cause is QMI client-side contention with WaveOS's own `uqmi-ubus` daemon (the exact class of contention `ubus`-first detection already exists to avoid — see above) silently returning a stale cached NAS report with no error, though this hasn't been proven beyond "the modem and ubus are both fine when queried independently, so something about `qmicli`'s own session is the remaining suspect." **Fixed**: `cmd/modem-exporter/staleness.go`'s `staleTracker` withholds a leg's `rsrp`/`rsrq`/`rssi`/`sinr` fields (writes nothing for them that tick, same "return nil, don't write" convention `radioCellPoint` already uses elsewhere) once they've been bit-for-bit identical for 3× `-interval`, logging `"stale metrics (age Ns)"` at most once a minute. Deliberately change-detection, not a source-provided timestamp — `qmicli`'s text output has none, so a timestamp-only mechanism (which `ubus`'s own `"timestamp"` field would support) would leave every other backend uncovered. Covered by `cmd/modem-exporter/staleness_test.go`, including a case with a genuinely frozen source. **Not yet deployed to `dawn6g`'s running `modem-exporter`** — the 2026-11-23 reboot (see above) means its current data is fresh again for now (confirmed via both `AT+QENG` and `ubus call qmi metrics` matching), but the same freeze can recur at any time until this ships.
