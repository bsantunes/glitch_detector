# Telemetry (InfluxDB/Grafana)

**Read `metrics-endpoint.md` first** — it's the authoritative handoff doc, written for Claude Code specifically, and its target schema matches what's actually implemented (unlike the `.docx`/`dawn6g-metrics/README.md`, which describe an earlier, superseded draft — see Repository Layout in the root `CLAUDE.md`).

The real server stack is **`~/dawn6g-metrics` on `wservices.wavesys.pt`** (Apache on the host, not Docker, is the sole public entry point and also serves Nagios — never take port 443 from it; InfluxDB/Grafana are Docker Compose, bound to loopback only). This repo's own `docker-compose.yml` is stale/unrelated (wrong org/bucket names, no TLS) — ignore it. Org `wavecom`; buckets `radio` (90d, modem signal/cell telemetry), `network` (90d, now live — TWAMP RTT/jitter/loss and `glitch-exporter`'s stall/retransmission stats, see below; still earmarked for future QoS/nDPI data too), `events` (365d, unused so far — future event-driven RadioEvent points), **`location`** (365d, device GPS/GNSS position, see below; deliberately its own bucket rather than folded into `radio`, since GPS isn't a radio metric despite coming from the same modem hardware).

**What `modem-exporter` writes today** (confirmed live on `aaeon`/`6global`/`dawn6g`, to `radio` only) — this matches `metrics-endpoint.md`'s target schema exactly, except `pci` (optional there, not implemented — see Known Issues in the root `CLAUDE.md`):
- `radio_cell`: tags `device`/`modem_id`/`method`/`rat`/`role` (+`plmn`/`tac` on anchor rows only); fields `rsrp`/`rsrq`/`rssi`/`sinr` (NaN-omitted) + `cell_id` (anchor rows only).
- `modem_state`: tags `device`/`modem_id`; fields `operator_name`/`registration_state`/`packet_service_state`.
- Uses `WriteAPIBlocking` + log-and-drop on failure (deliberate: avoids unbounded in-RAM buffering on constrained devices if InfluxDB is unreachable). Both `metrics-endpoint.md` and the `.docx`/README recommend the retry-buffered async `WriteAPI` (batch 500, flush 1000ms, 10 retries, 100k-point RAM buffer) instead — a real, repeatedly-suggested tradeoff worth reconsidering, not just a one-off idea.
- `metrics-endpoint.md`'s "TODO 1" (migrate off the old `modem_telemetry`/`device_id` schema) is **done**. Its "TODO 2" (provision the Grafana dashboard as JSON under `dawn6g-metrics/grafana/provisioning/dashboards/`) is **still open** — a dashboard exists and works in Grafana's live DB, but isn't captured as repo-tracked JSON yet (also true of a TWAMP panel/dashboard, not yet added — see below), so none of it survives the Grafana container's volume being lost/recreated. Datasource UID is `influxdb-flux` (Flux query language, default bucket `radio`).

**What `twamp-exporter` writes** (confirmed live on `aaeon`/`6global`/`dawn6g`, to `network`) — schema is new, not specified by `metrics-endpoint.md` (which only earmarks the bucket, not a schema):
- `twamp`: tags `device`/`reflector`, plus `iface` when `-bind-dev` is set (`v2.3.4`+); fields `rtt_ms`/`jitter_ms`/`loss_pct` (floats) + `sent`/`received` (ints), one point per probe burst (default interval 30s).
- **TWAMP path caveat (WaveOS boards).** On `dawn6g`/`6global`, ordinary internet traffic uses `lte1` (metric 40), but traffic to wservices goes over the wired `br-wan`: WireGuard's `route_allowed_ips` installs a host route for its endpoint `51.91.57.3` via `br-wan`, so TWAMP to `10.30.30.1` went through `wg0` over the wired link, and InfluxDB writes go to the public address over `br-wan` directly. **All `twamp` points before each board's switch measured the wired path, not cellular**: `6global` up to 2026-11-25 21:20:29.42 UTC (last wired point; first cellular point 21:21:02.30), `dawn6g` up to 2026-11-25 23:27:09.98 UTC (first cellular point 23:27:53.32). Since then both probe `51.91.57.3:862` with `-bind-dev lte1` (`iface=lte1`). There is no clear RTT jump at the switch: wired averaged ~57 ms on `dawn6g` (48–73 ms, the hour before) and cellular is ~50–60 ms, so filter on `iface`/`reflector`, not on an RTT step. The reflector's 862/udp is allowed by an explicit ufw rule on wservices.
- Same `WriteAPIBlocking` + log-and-drop pattern as `modem-exporter`, same reasoning.
- **A Grafana panel for this now exists** (built live in Grafana's UI — not yet repo-tracked JSON, same open "TODO 2" gap as the `radio` dashboard). Query:
  ```flux
  from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "twamp")
    |> filter(fn: (r) => r._field == "rtt_ms" or r._field == "jitter_ms" or r._field == "loss_pct")
    |> filter(fn: (r) => r.device =~ /^${device:regex}$/)
  ```
  Reuses the dashboard's existing `device` template variable (query: `tagValues(bucket: "network", tag: "device")`, multi-value on) — `:regex` formatting is what makes multi-select/"All" work with `=~`, since plain `==` only matches one value. Same `influxdb-flux` datasource as the `radio` panels, just pointed at the `network` bucket.

**What `glitch-exporter` writes** (confirmed live on `aaeon` — a test-3-style forced outage's `glitch_summary`/`glitch_event` points matched the kernel's own reported duration/steps exactly, and 10+ minutes of background-only traffic kept ticking `glitch_summary` with `stall_episodes=0` throughout; see the `glitch-detector-internals` skill for the detection logic this schema reports on), to `network`:
- `glitch_summary`: one point per `-interval` (default 10s), **always written even when every field is zero** — a heartbeat, unlike every other exporter's "skip if nothing to report" convention. Tags: `device`/`iface`. Fields: `stall_episodes` (int, count of `STALL_END`s this interval), `stall_max_ms`/`stall_sum_ms` (float, ms), `stall_open` (int, episodes started but not yet ended as of this point — a live snapshot, not an interval accumulator), `retrans_count` (int), `dropped_events` (uint, the delta of `glitch.Handle.Dropped()` since the last tick), plus its breakdown: `kernel_dropped_events`/`user_dropped_events`/`untruncated_over_limit_events` (uint, `afpacket.Capture`-only — always 0 for `-capture ebpf`, since the eBPF path has no equivalent split; see the `glitch-detector-internals` skill) and `write_queue_dropped_events` (uint, points dropped by the bounded queue in front of the InfluxDB write client when it couldn't keep up — see that same skill's write-queue note). Logged to the exporter's own journal each interval too, when nonzero.
- `glitch_event`: one point per `stall_start`/`stall_end`/`stall_abandoned` — never for a retransmission, which is counted only, via `glitch_summary.retrans_count`. Timestamped with the kernel event's own time (or, for `stall_abandoned`, the moment the 30s timeout was detected — there is no kernel event to read a time from for one). Tags: `device`/`iface`/`type`. Fields: `proto` (int), `src_port`/`dst_port` (int), `dst_ip` (string — **never a tag**, see below), `baseline_ms` (float), and — `stall_end`/`stall_abandoned` only — `duration_ms` (float) and `steps` (int, always 0 for `stall_abandoned`: the kernel only reports a step count on `STALL_END`, which by definition never arrived for an abandoned episode, so the real count is genuinely unknown, not a plausible-looking default). Rate-limited to `-max-events-per-sec` (default 20) points/second, shared across all three types — anything over the limit still counts in `glitch_summary`.
- **Deliberately never tags on an IP address or port anywhere** in this schema — unlike `radio_cell`'s `device`/`modem_id` or `twamp`'s `reflector`, a 5-tuple is high-cardinality and per-flow, not a stable grouping key; `dst_ip`/`src_port`/`dst_port` live only on `glitch_event`'s fields.
- `stall_abandoned`: if a connection dies mid-outage, `STALL_END` never arrives and the kernel-side episode state is lost with it. `glitch-exporter`'s own `Aggregator.CheckAbandoned` (run every 5s, independent of `-interval`) gives up on an open episode after 30s with no `STALL_END`, reports it with the duration measured so far, and drops it from the open set — it does **not** count toward `glitch_summary.stall_episodes`/`stall_max_ms`/`stall_sum_ms`, which are literal `STALL_END`s only.
- Uses the async, batching `WriteAPI` (not `WriteAPIBlocking`, unlike every other exporter here) — deliberate, since the ring-buffer reader must never block on InfluxDB.
- **Known gotcha, not a bug**: on `aaeon`, `glitch-exporter`'s own InfluxDB write traffic goes out over the same `wwan0` interface it's monitoring (no split-tunnel/separate management interface), so its own HTTPS writes are themselves counted in whatever stats it reports — a brief InfluxDB-direction hiccup can show up as a tiny, legitimate blip in its own numbers, not a sign the detector is wrong.
- No Grafana panel for this yet — same open "TODO 2"-style gap as `radio`/`twamp`'s own dashboards (see above), not yet captured as repo-tracked JSON.

**What `gps-exporter` writes** (schema confirmed suitable, but no real `gps_fix` point has actually landed in InfluxDB yet from a running exporter — `aaeon` obtained a real fix manually over AT, but its exporter isn't reading that path yet; see the `gps-integration` skill): measurement `gps_fix` in the `location` bucket. Tags `device`/`modem_id`/`method`; fields `latitude`/`longitude`/`altitude` (floats). **Only written when `Fix.Valid == true`** — skip the point entirely otherwise, same "return nil, don't write" pattern `radioCellPoint`/`modemStatePoint` already use, but for a different reason: `(0, 0)` is a real coordinate (Null Island), so unlike signal metrics there's no safe NaN-style sentinel for "no fix yet." Deliberately a **separate bucket**, not folded into `radio` — plan is to **join at query time** (Flux `join()` on the `device` tag against the latest `gps_fix` point) for map panels combining radio/network metrics with position, rather than denormalizing lat/lon onto every `radio_cell`/`twamp` point.

**Per-device tokens**: `./add-device.sh <id>` in `dawn6g-metrics/` on `wservices` — writes `secrets/devices/<id>.token` **and** `secrets/devices/<id>.authid` (the InfluxDB auth entry's own ID; `revoke-device.sh` needs this file and can't revoke by token value alone). `aaeon`/`6global`/`dawn6g` all have proper `.authid` files (`6global`/`dawn6g`'s earlier manually-created tokens, which lacked one, were rotated out — see below). **No in-place way to add a permission to an existing token** — this InfluxDB CLI's `auth` command only supports `create`/`delete`/`active`/`inactive`, no `update`; expanding a token's bucket scope means issuing a new one and rotating it in (create new → deploy → verify → revoke old — never revoke-then-recreate, to avoid a write-gap window).
On each gateway, the token is wired in as `INFLUX_TOKEN` — `/opt/dawn/modem-exporter.env` (mode 600) for systemd, baked into the `procd` init script for WaveOS. This diverges from `metrics-endpoint.md`'s documented on-device convention (`/etc/dawn6g/influx.token`, read directly as a file by the Go agent) — functionally fine since our services resolve the env var themselves, but worth knowing if anything else ever expects that exact path.
**All three device tokens, plus Grafana's read-only token, were rotated** to add `location`-bucket access (`add-device.sh`/`bootstrap.sh` now provision/scope all four buckets for new tokens automatically). One gotcha hit during the Grafana token rotation: a Docker Compose file-based secret is mounted into the container with the **exact host file permissions/ownership**, not normalized — `chmod 600`-ing the secret file (seemed like better hygiene) broke Grafana's ability to read it (its container runs as a different UID than the host file owner), surfacing as `provisioning: open /run/secrets/...: permission denied`. Match the original file's mode (`644`) when touching these secret files, don't tighten them.
**Known cleanup opportunity, not yet done**: a stale, pre-`add-device.sh` token literally named `dawn6g` (not `device:dawn6g`), write-scoped to `radio` only, is still sitting unrevoked in InfluxDB (`influx auth list` will show it) — it predates this repo's current token conventions and isn't used by anything live, but hasn't been cleaned up.

**Known deployed devices** (2026-11-25): **`dawn6g`** and **`6global`** are the priority boards — both WaveOS Supermicro, SIMCom SIM8262E-M2 (`lte0`/`mwan0`, no SIM/not used) + Quectel RM520N-GL (`lte1`/`mwan1`, carries the traffic), all four exporters at `v2.3.4`. `dawn6g` (`10.10.10.201`) has had a real SIM and antennas since 2026-11-10 (NOS). `6global` (`10.10.10.184`) went live 2026-11-25 with a MEO SIM and antennas; its SIM was PIN-locked (`netifd`: `PIN not specified but required`) — PIN verified once and the lock disabled with `qmicli --uim-set-pin-protection` (no PIN stored in the config), after which `mwan1` came up by itself. **`6global` reports one leg (NR, `role=anchor`, SA, band n77) while idle and two legs (LTE `anchor` + NR `scg`, EN-DC) once its data session is up.** Its GNSS antenna is on the Quectel (AT on `usb:2c7c:0801:03`). **`aaeon`** (Debian) has no SIM and no antennas any more: it is the **build machine only** and can't gather modem data; its four exporters are to be stopped and disabled (binaries, the `/dev/dawn-gps` udev rule and the `gps-exporter` NMEA drop-in stay in place). Silence from `aaeon` in InfluxDB once they're stopped is expected.

## Deployment context per board (moved from CLAUDE.md)

- `dawn-agent.service`: systemd unit; runs `init_gateway.sh` first, then the agent from `/opt/dawn`. **Superseded** — not installed on `aaeon` (`systemctl is-enabled dawn-agent` → `not-found`); `glitch-exporter.service` + `twamp-exporter.service` + `modem-exporter.service` cover what it used to do.
- `glitch-exporter.service`: was installed and running on `aaeon` (eBPF; `Conflicts=dawn-agent.service`) — being stopped/disabled now that `aaeon` is build-only. Runs on `dawn6g` and `6global` via `openwrt/glitch-exporter.init` with `-capture afpacket -iface lte1` (`v2.3.4`; the eBPF path doesn't exist on WaveOS).
- `init_gateway.sh`: loads kernel modules, configures the modem's dedicated QoS bearer via AT commands (DSCP EF / cid 2), and sets up HTB traffic shaping with a priority lane for EF-marked traffic.
- `modem-tool.service`/`modem-exporter.service`/`twamp-tool.service`/`twamp-exporter.service`: systemd units for the Debian gateway; `openwrt/*.init` for WaveOS (`procd`). The exporters run on `dawn6g` and `6global` (`v2.3.4`); the `-tool` services are not enabled anywhere (`6global` had them running from an old install until 2026-11-25). `aaeon`'s units are being stopped/disabled (build-only).
- `gps-exporter.service`/`openwrt/gps-exporter.init`: **`gps-exporter` runs on `dawn6g` and `6global`** (procd, `-method at -port usb:2c7c:0801:03`, `v2.3.4`; `dawn6g`'s init script was moved off `/dev/ttyUSB10` and its duplicate `-interval` removed on 2026-11-25; `6global` uses the repo template). Both write a `gps_fix` on every 30 s poll with no `stty` involved (6global's old Nov 13 build ran `stty` per poll, failed, and also touched the SIMCom's `ttyUSB5`). `aaeon` ran `v2.3.2` with `-nmea-port usb:1e0e:9001:01` (systemd drop-in) since 2026-11-24 — its first NMEA point carries `hdop=500`, the receiver's "unknown", which `v2.3.3`+ writes as missing; now being stopped (build-only). `gps-tool.service`/`openwrt/gps-tool.init` aren't installed anywhere.
