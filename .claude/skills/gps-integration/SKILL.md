# `gps/` package

Reads GPS/GNSS fixes from a modem's own GNSS receiver. Deliberately a standalone package (own process, `gps-tool`/`gps-exporter`) — not wired into `dawn-agent`'s active-monitoring loop or folded into `modem/`'s stateless per-call backend shape, because the QMI backend genuinely needs a different shape (see below).

**Fleet-wide status**: `gps-exporter` runs on `aaeon` and `dawn6g` via AT-over-serial. `6global` is switched off on purpose (no antennas, no SIM) and runs no exporters; before that, `gps-exporter` ran cleanly there too (confirmed live, sustained, zero real errors on the SIMCom modems — no fix, no antenna on that leg). **`aaeon` has a working GNSS antenna, and so does `dawn6g`'s second modem (Quectel RM520N-GL)** — both have gotten real fixes (`6global` still has no antenna connected on either modem). Manual AT-over-serial testing on `aaeon` tracked real GPS satellites (04/27/28/31) and GLONASS (83) at 25-35 dB-Hz and obtained a valid fix: `$GPRMC,192721.00,A,4132.984808,N,00824.784113,...`, decoding to **41.549747, -8.413069** (Portugal). **⚠️ That fix was wrong — ~340 m off** (an indoor fix from few weak satellites): `aaeon`'s NMEA port later gave a stable 41.548033, −8.416445 (2026-11-24, 16 fixes within 0.2 m, ~3 m from `dawn6g`'s own fix in the same lab). Don't use the 2026-11-18 value as a reference. The earlier "no antenna" theory for `aaeon`'s ModemManager `GeneralError` (below) is therefore **disproven**: the antenna works, the receiver tracks satellites and fixes fine over AT; whatever causes ModemManager's own enable call to fail is a separate, unknown issue that is deliberately not being investigated — see that bullet. **`aaeon`'s `gps-exporter` is now enabled and running there too**, via the AT backend on its dedicated reserved port (`/dev/dawn-gps`, Phase C) — Phase D's live test confirmed the reader itself works correctly (no parse errors across a run), though no real fix has landed yet outside that one manual test. Re-checked 2026-11-24: zero `gps_fix` points from `aaeon` in InfluxDB over 30 days (`dawn6g`'s are arriving). The running binary was a pre-`v2.3` build (2026-11-18, no `-version`), still printing the pre-`9fc3d36` per-poll `stty /dev/dawn-gps: unable to perform all requested operations` warning and lacking that commit's `+CGPSINFO`-after-`OK` reader fix — which alone explains zero fixes. Upgraded to `v2.3.1` the same day (15:35 UTC, old binary at `/opt/dawn/gps-exporter.prev`): 10 min later, 21/21 polls parsed cleanly (`OK` then an empty `+CGPSINFO: ,,,,,,,,` → "no fix yet"), no `stty` warnings, still no fix — the antenna is indoors and the only manual fix needed XTRA. `dawn6g`'s Quectel got a real fix too, straight through `gps-tool`/`gps-exporter`'s own code this time (not just manual AT testing) — see the AT-over-serial bullet below for that, the reader bug it surfaced and fixed, and the real (non-reader) issue still open there.

**⚠️ Third incident, this one on `aaeon` (production Debian gateway) — `gps-exporter` was stopped+disabled there afterwards; it has since been re-enabled on the AT backend only (`/dev/dawn-gps`, see Fleet-wide status), never ModemManager's Location interface:**
1. `aaeon`'s GPS-engine-enable (`mmcli --location-enable-gps-raw`) had already failed earlier with a `GeneralError` of unknown cause — the antenna is confirmed working (see the ModemManager bullet below) — `gps-exporter` was still deployed and left polling every 30s regardless, since a failed enable isn't fatal by design (same as every other backend).
2. Those repeated `--location-get` polls started failing with `modem has no location capabilities`, then — after ModemManager picked up a PolicyKit rule change (see below) — with `Unauthorized: PolicyKit authorization failed: not authorized for 'org.freedesktop.ModemManager1.Location'`. A new rule, `/etc/polkit-1/rules.d/49-modemmanager-location-root.rules`, was added to grant root that action explicitly (ModemManager's default policy requires `allow_active`, which doesn't cleanly apply to a non-interactive root systemd service — no rules.d files existed on this box at all before this one).
3. A `sudo systemctl restart ModemManager` (tried to force it to re-probe location capabilities) triggered `[/dev/cdc-wdm0] endpoint hangup` / `fatal error initializing: modem is unusable` during ModemManager's own internal QMI version-info handshake — **the same corruption signature as the two `6global` incidents**, but this time via ModemManager's own internal QMI client, not raw `qmicli`, and on a third distinct modem (this board's SIMCom). `ModemManager` has shown `No modems were found` ever since.
4. **Production impact was real but limited, not an outage**: `modem-exporter`'s own cascade fell through to its raw-QMI fallback during the window ModemManager had no modem (the already-documented startup-race behavior, just self-triggered this time) — confirmed via live InfluxDB queries that real signal/registration data kept flowing the whole time via that fallback. Best-guess cause: `modem-exporter`'s raw-QMI fallback client and ModemManager's own reinitializing client raced for the same physical QMI channel on `/dev/cdc-wdm0` at the same moment — the same *class* of contention the `ubus`-priority design already exists to avoid on WaveOS, just not something this Debian board's architecture has an equivalent guard against.
5. Decision (matching the `6global` incidents' handling): leave `ModemManager` as-is rather than force another restart attempt — production data is flowing fine via the fallback, so there's no urgency, and repeated recovery attempts are exactly what's caused escalation twice already. `gps-exporter` was stopped and disabled on `aaeon` (`sudo systemctl stop gps-exporter && sudo systemctl disable gps-exporter`) so it can't repeat this pattern on a future reboot. **Don't re-enable it there, and don't attempt another `ModemManager` restart/reinit, without a real plan** — same spirit as the QMI-backend disable above, now extended to ModemManager's Location interface specifically on this board. (See the root `CLAUDE.md`'s Hard Rules.) Later superseded for the AT backend only: `gps-exporter` was re-enabled on `aaeon` with `-method at -port /dev/dawn-gps`, which never touches ModemManager — the ModemManager prohibition still stands.

**Phase C (reserving a dedicated AT port for GPS) — done on `aaeon`.** A udev rule reserves the SIMCom's secondary AT port (ModemManager's `AT_SECONDARY` role — its primary AT port, `AT_PRIMARY`, was deliberately *not* chosen, since that one isn't safe to take away from ModemManager) exclusively for GPS, matched by vendor/product ID plus USB interface number rather than by `ttyUSB` index (which can shift across boots/kernel versions): `/etc/udev/rules.d/99-dawn-gps.rules` —
```
SUBSYSTEM=="tty", ATTRS{idVendor}=="1e0e", ATTRS{idProduct}=="9001", ENV{ID_USB_INTERFACE_NUM}=="03", ENV{ID_MM_PORT_IGNORE}="1", SYMLINK+="dawn-gps"
```
`ID_MM_PORT_IGNORE=1` is the same property ModemManager's own shipped rules use to mean "never touch this port" — and the same property `modem.DetectAT`'s AT fallback now skips (commit `1ee26b6`, added specifically so `modem-exporter`'s AT fallback and `gps-exporter` could never fight over this port; confirmed first that `modem-exporter` on `aaeon` uses ModemManager, never AT, so this was a defense-in-depth fix, not one closing a live collision). Validated with `udevadm test` (dry run) before rebooting: `ttyUSB3` matched (`ID_MM_PORT_IGNORE=1` set, `dawn-gps` symlink added), `ttyUSB2` (the primary AT port) matched neither. After the reboot: `ttyUSB3` shows as `ignored` in `mmcli`'s own port list, `/dev/dawn-gps` → `ttyUSB3`, `fuser` confirms no process holds it, and `wwan0`/`modem-exporter`/`twamp-exporter`/`glitch-exporter` all stayed up and connected straight through the reboot. A manual `AT+CGPSXE?` over `/dev/dawn-gps` afterward confirmed XTRA assistance data (enabled by hand earlier) **persists across a reboot** — it's stored in the modem, not reset per-session, which matters for Phase D's cold-start comparison below. Rollback, if ever needed: `sudo rm /etc/udev/rules.d/99-dawn-gps.rules && sudo udevadm control --reload-rules && sudo reboot`. Full procedure (rule, dry-run validation, post-reboot checks, rollback) is in `DEPLOYMENT.md`.

`Supports(method)` — **ModemManager and AT-over-serial are enabled; raw QMI is deliberately disabled** (see the root `CLAUDE.md`'s Hard Rules):
- **ModemManager**: `gps-raw` location source reports already-parsed decimal `modem.location.gps.{latitude,longitude,altitude}` directly — no NMEA parsing needed. Enabled via `--location-enable-gps-raw` (root/PolicyKit-gated, retried the same way `modem/mmcli.go`'s `runMmcliSetup` does). **On `aaeon`, enabling it fails**: `sudo mmcli -m 0 --location-enable-gps-raw` →
  ```
  error: couldn't setup location gathering: 'GDBus.Error:org.freedesktop.ModemManager1.Error.MobileEquipment.PhoneFailure:
  QMI protocol error: Couldn't enable location 'gps-raw' gathering: Couldn't start GPS engine: QMI protocol error (46): 'GeneralError''
  ```
  **This was previously theorized as a missing GPS antenna on `aaeon` — that theory is now disproven.** Manual AT-over-serial testing (see "Fleet-wide status" above) confirmed `aaeon` has a working GNSS antenna: real satellites tracked at 25-35 dB-Hz and a valid fix obtained. The real cause of this `GeneralError` is **unknown and deliberately not being investigated** — candidates include the GNSS engine already being started over AT when ModemManager's own QMI-based enable runs, the modem's firmware expecting a different QMI location service than the one ModemManager targets, or QMI client contention (the same general class of issue documented elsewhere in this section) — but the AT-over-serial backend below avoids ModemManager's location interface entirely, making this moot for `aaeon`'s actual GPS path going forward. Per this project's Hard Rules: **never call `mmcli --location-*` on `aaeon`, and never restart ModemManager there** (see the incident writeup above for why that specifically is dangerous on this board). The ModemManager code path itself remains implemented and otherwise ready; it's just not the backend `aaeon` will use.
- **AT-over-serial (`gps/at.go`) — confirmed live, sustained, zero errors on `6global` and `dawn6g` via their SIMCom modems (no fix there — no antenna on either board's SIMCom leg).** SIMCom (`AT+CGPS=1,1`/`AT+CGPSINFO`) and Quectel (`AT+QGPS=1`/`AT+QGPSLOC=2`); both enable their GNSS engine and poll cleanly. **On `aaeon`'s SIMCom modem, manual testing (run by hand over the AT port, outside `gps-exporter` itself) got a real fix** — but only after also enabling SIMCom's XTRA assistance data (`AT+CGPSXE=1`), which the engine doesn't request on its own: with `AT+CGPS=1,1` alone, the receiver tracked real satellites (25-35 dB-Hz) but never resolved a position; with XTRA also enabled, `AT+CGPSINFO` returned a valid fix within a reasonable wait. This is now wired into `gps/at.go`'s enable sequence (`enableAssistanceData`, `-agps` flag, default on). `modem.PortInUse` (scans `/proc/*/fd`) makes `DetectAT` skip any serial port another process already has open — specifically written to avoid the kind of port collision that caused the QMI incidents below, since WaveOS's `uqmi-ubus` daemon holds its own AT ports open continuously for PCI/EARFCN polling. Two real bugs surfaced and fixed via this live testing, both in shared `modem/at.go` (so they also improve `modem.Detect()`'s own AT fallback, not just `gps/`): `parseATI` was misreading a Quectel's unsolicited `+CPIN: NOT INSERTED` spam (arriving before its actual `ATI` reply) as the manufacturer/model string; and the enable retry loop was treating "GNSS already running" (SIMCom: plain `ERROR`; Quectel: `+CME ERROR: 504`) as a failure to retry past, rather than querying the vendor's own state command and accepting confirmed-already-on as success.

  **`dawn6g`'s Quectel RM520N-GL has antennas fitted and got a real fix via `gps-tool -method at -port /dev/ttyUSB10` (that board's two modems mean the port needs pinning — see the WaveOS port-stability note below):** `lat=41.548050 lon=-8.416490`, cross-checked against simultaneous raw NMEA on a second port (`$GPRMC` → 41.548052,-8.416491) — matches to 1e-6. **This settles the previously-open Quectel longitude-sign question: `AT+QGPSLOC=2`'s sign is correct on this firmware.** The community-reported western-longitude sign bug does not reproduce here, though it may still exist on other Quectel firmware.

  **⚠️ Bug found and fixed via this same live testing: `gps-tool`/`gps-exporter` alternated between a real fix and "no GPS fix yet" on `dawn6g`, even though simultaneous NMEA on a second port showed a continuous fix (86/86 valid `$GPRMC` sentences over 60s).** Root cause, confirmed live on both `dawn6g`'s Quectel and `aaeon`'s SIMCom: `stty -F <dev> 115200 raw -echo` fails ("unable to perform all requested operations") on these virtual USB-serial (CDC-ACM-style) ports specifically because of the explicit baud argument — confirmed by testing with/without it on both boards, not assumed — so `-echo` never actually takes effect, and because `atTransact`'s read loop stops as soon as it sees a complete reply and never drains what the modem sends afterward, trailing bytes from one exchange linger in the port's input queue and can get read as part of the *next* command's response. The two problems combine badly: a stale `+CME ERROR: 516` left over from a previous poll landed in the same buffer as a genuinely fresh, valid `+QGPSLOC:` line, and the original `parseQGPSLOC` checked for a CME error *before* ever looking for real data — so it reported "no fix" despite the real fix being right there in the same buffer. Fixed three ways: (1) dropped the baud argument from `stty` (confirmed live that `raw -echo` alone succeeds where `115200 raw -echo` fails, on both boards); (2) `atTransact` now drains any stale bytes already sitting in the port's input buffer before writing each new command (`drainPort`, via a short `SetReadDeadline`); (3) `parseQGPSLOC`/`parseCGPSINFO` now check for a real data line *before* an error/empty reading, and take the *last* occurrence of either if more than one is present, so a real answer always wins over stale leftovers. `getFixAT` also now logs the raw AT response whenever a poll classifies as "no fix", so a misread like this is visible in logs instead of looking like "no antenna yet". Covered by `gps/at_test.go`'s `TestParseQGPSLOC_StaleErrorBesideFreshFix`/`TestParseCGPSINFO_StaleEmptyBesideFreshFix`, reproducing the exact contaminated-buffer shape seen live.

  **This fix is confirmed live on `dawn6g` (briefly stopping the production `gps-exporter` to test without port contention, then restarting it) to eliminate the *misread* — raw "no fix" responses are now clean, single, uncontaminated `+CME ERROR: 516` replies, never a mix of a stale error and a fresh fix.** It does **not** fully resolve the alternating pattern on its own: `AT+QGPSLOC=2` still intermittently returns a genuine (not contaminated) `+CME ERROR: 516` even while NMEA on the other port shows a continuous lock. Leading candidate, not yet confirmed: `AT+QGPSXTRADATA?` on this board reports `0,"1980/01/06,00:00:00"` — XTRA assistance data accepted (`AT+QGPSXTRA=1` → OK) but never actually valid — see the XTRA follow-up item below. **Phase D's "must report a fix on every poll" bar is therefore not yet met on `dawn6g`** — the reader-level bug is fixed and verified, but a second, real issue (intermittent `AT+QGPSLOC=2` fix-confidence, not a parsing bug) remains open. The fix above has **not yet been redeployed** to `dawn6g`'s running `gps-exporter` (still the pre-fix binary) — redeploying it, and a longer supervised test, are both pending.

  **Follow-up, not done yet:**
  - **Quectel XTRA data never validates** (`AT+QGPSXTRADATA?` → `0,"1980/01/06,00:00:00"`, i.e. invalid, epoch-zero timestamp) despite `AT+QGPSXTRA=1` being accepted. Quectel's documentation suggests this may need a module restart plus explicit time injection (`AT+QGPSXTRATIME`) to actually take effect — not yet tried, and not yet wired into `gps/at.go`'s enable sequence if it turns out to matter. Plausibly related to the intermittent `516` issue above.
  - **Done**: `-port` now also accepts `usb:<vid>:<pid>:<ifnum>` (e.g. `usb:2c7c:0801:03`), resolved via sysfs at startup by `modem.ResolvePort` (`modem/usbport.go`) — walks `/sys/class/tty/ttyUSB*`/`ttyACM*`, matching each candidate's own `bInterfaceNumber` and its parent USB device's `idVendor`/`idProduct`. Works identically on WaveOS and Debian (plain sysfs, no `tc`/udev dependency); confirmed live resolving `usb:2c7c:0801:03` → `/dev/ttyUSB10` on `dawn6g`. `openwrt/gps-exporter.init`/`openwrt/gps-tool.init` now use this (`GPS_PORT=usb:2c7c:0801:03`, the Quectel's secondary AT port) instead of a hardcoded `ttyUSB` number, so a reboot that shifts `ttyUSB` numbering (two modems present) no longer silently points at the wrong device. A plain device path (`/dev/dawn-gps`, `/dev/ttyUSB3`) still works unchanged — `aaeon`'s udev-rule approach and this `usb:` spec are two ways to the same end, not a replacement of one by the other.
- **Raw QMI (`qmicli`) is implemented but deliberately disabled** (`Supports`/`NewPoller` both refuse it — see ⚠️ below). The code (`QMISession`) is real and was confirmed working against a SIMCom modem (real NMEA sentences streaming, no fix — no antenna), but is gated off after repeatedly corrupting production QMI client state — see the incident writeup below before ever re-enabling it.
- `ubus`/`uqmi` are **not implemented**: `ubus`'s `"location"` method only returns cell-ID/LAC-CI data, never real GPS coordinates, despite the name (would need a patch to the vendor's `uqmi-ubus.lua` — assessed as feasible in principle, since it already runs `AT+QENG` for PCI/EARFCN and discards those too, but not attempted); `uqmi` lists `pds` as a service name but exposes no actual PDS/location CLI action.

**NMEA reader (`gps/nmea.go`, `-nmea-port`) — added as an alternative fix source, additive-only, opt-in.** Motivation: `AT+QGPSLOC=2` can report "no fix" even while a continuous lock is held (see the `⚠️ Bug found and fixed` entry above) — a modem's dedicated NMEA port (interface 01 on both SIMCom and Quectel) streams `$G{P,N,L}RMC`/`GGA` sentences independently of that command. `NMEAReader` combines the two: RMC's `A`/`V` status field is the sole authority for `Fix.Valid` (GGA never touches it), GGA supplies `Satellites`/`HDOP`/`Altitude` (RMC has no altitude field at all). AT still owns engine start/stop and assistance data — NMEA ports don't accept AT commands. New `-nmea-port` flag on `gps-tool`/`gps-exporter` (same `usb:<vid>:<pid>:<ifnum>`/plain-path forms as `-port`); empty by default, so no board's behavior changes unless it's explicitly set. `Fix` gained additive-only fields (`SpeedKnots`/`CourseDeg`/`HDOP` — NaN when unavailable, same convention as `modem/`'s `Signal`; `Satellites`; `Source` `"at"`/`"nmea"`, so a zero `Satellites` can be told apart from "not populated"); `gps_fix` gained a matching additive `source` tag and `speed_knots`/`course_deg`/`hdop` (NaN-omitted)/`satellites` fields, written only for an NMEA-sourced point — see the `telemetry-schema` skill.

A real shutdown-hang bug was caught and fixed before this shipped: a first version read the port with a blocking `bufio.Scanner`, relying on a second goroutine's `f.Close()` to unblock it on shutdown — confirmed live on `dawn6g` that this does not reliably interrupt a pending `Read` here the way it can for a `net.Conn`, and the process hung until force-killed. Rewritten to use the same `SetReadDeadline`-based bounded-read loop `gps/at.go`'s `drainPort` already relies on, checking `ctx.Done()` between reads instead.

**⚠️ Live verification incomplete — do not deploy `-nmea-port` to a running `gps-exporter` without resolving this first.** On `dawn6g`: `usb:2c7c:0801:01` correctly resolves to `ttyUSB8` (re-confirmed against current sysfs, unchanged since the original manual investigation that found 86/86 valid RMC there), and `AT+QGPSCFG` confirms the modem's own config is as expected (`"nmeasrc",1`; `"outport","usbnmea"`) — but a live, multi-minute read of that port (both through the Go reader and independently via a raw `cat`) showed **zero NMEA data arriving**, unlike the original capture. Not yet understood — candidates include repeated `AT+QGPS=0`/`AT+QGPS=1` engine cycling having left streaming off despite the config still reading as enabled, or `"usbnmea"` not actually mapping to interface 01 the way assumed. Needs a fresh investigation (ideally starting from a clean engine state) before `-nmea-port` can be trusted in production on either WaveOS board.

**`aaeon` (SIMCom SIM8202G) — NMEA is the only working fix source (2026-11-24).** With the engine running (`+CGPS: 1,1`) and XTRA on, `AT+CGPSINFO` and `AT+CGNSSINFO` both stayed empty while the NMEA port (`ttyUSB1` = `usb:1e0e:9001:01`, interface 01; ModemManager labels it "gps" but Location stays off) streamed valid `$GNRMC … A` at 1 Hz. So: **SIM8202G → `-nmea-port`; Quectel RM520N-GL → AT for now.** 10-min `gps-tool -method at -port /dev/dawn-gps -nmea-port usb:1e0e:9001:01` run (after a manual `TCOFLUSH` workaround, see below): 16/19 polls fixed, all `source=nmea`; satellites 3 (1×), 5 (4×), 6 (11×); HDOP 1.8–2.9 plus one 30.7 right before the receiver itself dropped to `$GNRMC,,V` / GGA quality 0 (indoor antenna — a real loss, not a reader fault); 16 positions within 0.2 m of their mean 41.548033, −8.416445, ~2.8 m from `dawn6g`'s 2-hour mean. No AT fallback logged — `v2.3.1` has none to log.

**Three `v2.3.1` NMEA-reader bugs found on `aaeon`, all fixed in `v2.3.2`:**
1. **`stty` hang.** `ttyUSB1` comes up after boot in cooked mode with echo on, so every NMEA byte is echoed back toward the modem, whose NMEA interface never reads it. GNU `stty` applies settings with TCSADRAIN, which waits for that output to drain — forever (`stty` stuck in the kernel's `set_termios`; `-drain` alone didn't help either, a `TCOFLUSH` did). The reader never opened the port and every poll silently said "no fix". Reproduced on demand by `stty -F /dev/ttyUSB1 sane` + ~10 s of NMEA. Fix: `modem.OpenRawSerial` — `O_NONBLOCK|O_NOCTTY` open, cfmakeraw with TCSETS (TCSANOW), then `TCIOFLUSH`; no external command; used by the NMEA reader and both AT backends. Note a pty does *not* reproduce this hang (no pending-output accounting), so the hardware run is the real regression check.
2. **Shutdown hang.** `NMEAReader.Close` waited on the reader goroutine stuck behind that `stty`, so SIGTERM didn't stop `gps-tool` (needed `kill -9`). Fix: port setup runs in its own goroutine and is abandoned on cancel; `Close` waits at most 2 s; AT port setup is bounded by the exchange timeout.
3. **No AT fallback** when the NMEA stream goes stale, though the approved design required it. Fix: `Poller.Fix` polls AT while no RMC/GGA sentence has arrived for 5 s (including a reader that never starts), switching back when the stream resumes; each switch logged once. **Required before `-nmea-port` is used on `dawn6g`'s Quectel.**

**`v2.3.2` on `aaeon` (2026-11-24).** All three fixes in tag `v2.3.2` (`624859d` termios, `1634923` shutdown, `e06be57` fallback, `512be19` tests; tests pass with `-race` on `aaeon`). Pre-tag hardware check: with `ttyUSB1` reset via `stty sane`, the old `stty raw -echo` hung again (rc 124 under `timeout 5`), while the new build opened the port, got a fix on its first poll, and stopped promptly on SIGTERM. 10-min `gps-tool` run from that same echo state, no manual flush: 3/19 polls with a fix (all `source=nmea`, 3–4 sats, HDOP 2.3–3.7, within 0.1 m of each other, ~2.5 m from `dawn6g`); the other 16 "no fix" were correct — the raw stream showed `$GNRMC,,V` and GGA quality 0 with 10 GPS satellites in view and none used (indoor reception, worse than an hour earlier). No fallback switches, no errors. **One open issue**: a GGA HDOP of `500.0` (the receiver's "unknown" value) arrived with a valid RMC and would be written as a real `hdop` field — filter it next release. Deployed as `gps-exporter` `v2.3.2` with `-nmea-port usb:1e0e:9001:01` via a systemd drop-in (`gps-exporter.service.d/nmea.conf`, unit file untouched; old binaries `/opt/dawn/gps-exporter.v2.3.1` and `.prev`); after a reboot (22:55) it started by itself, set up the port from its post-boot echo state, no stuck setup, no fallback switches.

**`gps.Detect`/`gps-tool`/`gps-exporter` do NOT reuse `modem.Detect()`'s cascade result** — that cascade prioritizes `ubus` over raw QMI specifically to avoid QMI client contention, but `ubus` has no GPS support at all, so naively using its pick means they'd find nothing on any WaveOS board. Instead `gps.Detect` tries ModemManager, then raw QMI/MBIM, then AT — but unlike `modem.Detect()`, it doesn't stop at the first step that finds *any* modem, only at the first step that finds one `Supports` will actually use (`anySupported`). That distinction matters on WaveOS specifically: raw `qmicli` reliably answers `cdc-wdm0`/`cdc-wdm1` (so a naive "first non-empty result wins" cascade would stop there), but every modem QMI finds is currently unusable for GPS (disabled) — without the `anySupported` check, AT would never be reached at all.

**⚠️ Raw QMI backend disabled after two separate production incidents — read before touching `Supports`/`NewQMISession`:**
1. **First incident**: manually killing `qmicli --loc-follow-nmea` with `timeout` (SIGTERM, but `qmicli` doesn't release its QMI client cleanly on it) against `6global`'s Quectel (`/dev/cdc-wdm1`) left its QMI control endpoint hung (`CID allocation failed... endpoint hangup`) for *every* process on that device node, not just the one killed — this also broke the production `uqmi-ubus` daemon's own access to that modem, taking down `modem-exporter`'s telemetry for it. Restarting `qmi-proxy`/`uqmi-ubus` did **not** recover it; only a board reboot did.
2. **`QMISession.Close()` was fixed** to call `--loc-stop` first (letting `--loc-follow-nmea` exit on its own) and only force-kill as a timeout fallback, specifically to prevent a repeat.
3. **Second incident, despite that fix**: a single, clean `gps-exporter` test run against `6global` (SIMCom, `/dev/cdc-wdm0`, no abrupt kill involved — session ended via the new graceful `Close()` path) still left that device's raw QMI client state corrupted afterward (`CID allocation failed... Service mismatch`), confirmed moments later and still broken after a short wait (not a transient race). Production (`ubus`-based `modem-exporter`) was **not** affected this second time, but direct `qmicli` access to that device was.

**Root cause, with a concrete candidate fix found via research (not yet tried live):** `qmicli` gives every separate invocation (`--loc-start`, `--loc-follow-nmea`, `--loc-stop`) its own throwaway client ID (CID), auto-released on exit — but LOC's start/follow/stop is meant to be *one* session spanning three processes, which libqmi mailing-list threads describing this identical symptom say requires explicitly carrying one CID across all three via `--client-cid=N --client-no-release-cid`. Our original code let each step grab its own anonymous CID, so `--loc-stop` was very plausibly stopping a different, irrelevant client than the one `--loc-follow-nmea` actually held — meaning it could never cleanly end *that* process's session regardless of the graceful-`Close()` fix, explaining why the fix didn't prevent the second incident. Medium-high confidence in this diagnosis (well-supported by multiple independent upstream threads with the identical pattern and fix), but **not verified against our actual incident** — desk research, not a confirmed root-cause analysis. Key sources: [libqmi#38](https://gitlab.freedesktop.org/mobile-broadband/libqmi/-/issues/38), [libqmi-devel: QMI LOC improvements (2018)](https://lists.freedesktop.org/archives/libqmi-devel/2018-July/002916.html), [libqmi-devel: CID leak consultation (2021)](https://lists.freedesktop.org/archives/modemmanager-devel/2021-December/009055.html).

Since AT-over-serial now works and makes QMI unnecessary for GPS on these boards, **there's no pressing need to re-enable or test this fix** — but if QMI GPS is ever revisited, rewriting `QMISession` to hold one CID across `--loc-start`/`--loc-follow-nmea`/`--loc-stop` (instead of letting each grab its own) is the single most actionable thing to try first, and should still be tested very conservatively (one controlled session, not repeated cycling) before trusting it in production again. **Do not re-enable `Supports(modem.MethodQMI)` or call `NewQMISession` against `6global`/`dawn6g` without that fix and a real plan for the remaining risk** (see the root `CLAUDE.md`'s Hard Rules).

## Known issue: QMI LOC client corruption (moved from CLAUDE.md)

- **QMI's location/LOC subsystem can corrupt QMI client state (`endpoint hangup`) for reasons not yet fully understood, across more than one access path.** Three separate incidents: twice on `6global` via raw `qmicli` LOC sessions (disabling the raw-QMI GPS backend as a result — see the `gps-integration` skill), and once on `aaeon` via **ModemManager's own internal QMI client** while its Location interface was being exercised repeatedly, unrelated to raw `qmicli` misuse that time. `gps-exporter` was stopped/disabled on `aaeon` as a result and later re-enabled on the AT backend only (`/dev/dawn-gps`, no ModemManager Location calls) — see the incident writeup above before changing that or attempting another `ModemManager` restart on that board (see also Hard Rules).
