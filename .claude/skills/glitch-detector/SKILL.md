# `glitch/` package — stall & retransmission detection internals

eBPF passive monitor: detects TCP retransmissions and reports stall episodes on an interface's egress path, gated so an idle connection is never mistaken for a stuck one. `glitch.Open(iface)` loads `bpf_src/tc_glitch.bpf.c`'s compiled object (embedded via `go:embed`, so `glitch/tc_glitch.o` must exist at compile time — `make embed`/`make glitch/tc_glitch.o` before a bare `go vet`/`go test`), attaches **two** eBPF programs on the same `clsact` qdisc, and decodes its ring-buffer events into a clean `Event{Time, SrcIP, DstIP, SrcPort, DstPort, Value, Baseline, Type, Steps, Proto}`.

**⚠️ WaveOS feasibility re-checked this session (priority shifted to `dawn6g`/`6global`) — still not supported, confirmed via the real code path, not just `tc`/`modprobe`:** `dawn6g`'s kernel (`5.15.167`) has no `.ko` module anywhere under `/lib/modules/$(uname -r)` for `cls_bpf`/`sch_ingress`/`act_bpf` (none built as loadable modules), and a small Go probe using the exact same `vishvananda/netlink` `QdiscAdd` call `glitch.Open()` itself makes — tried against `dummy0`, a genuinely idle, non-production interface, never a live one — fails with `no such file or directory` (ENOENT), the same symptom originally documented. **Did not run `modprobe`** for `cls_bpf`/`sch_ingress`/etc. — that would attempt to load a kernel module, which wasn't authorized. The base BPF subsystem itself does appear present (`/sys/fs/bpf` is mounted), so an XDP-based redesign (no `clsact`/TC dependency) is a theoretical option worth a real feasibility pass if eBPF on WaveOS is still wanted — not evaluated this session, and the current `tc_glitch.bpf.c` has no XDP equivalent to test. **Data-path mapping on `dawn6g`** (for whichever interface any future attempt would target): modem 0 (SIMCom) is `lte0`/`mwan0` (`/dev/qmi0`, `/etc/config/network` `disabled '1'`) — down, zero traffic; modem 1 (Quectel) is `lte1`/`mwan1` (`/dev/qmi1`, enabled) — up, carries the live default route and all real data traffic. **`6global` is switched off (no antennas/SIM — see the `telemetry-schema` skill's "Known deployed devices") and not re-checked independently** — same WaveOS image/kernel version as `dawn6g` is the working assumption for when it's brought back, not confirmed.

**Phase 1 of unifying the detection algorithm behind either capture method — done.** Given WaveOS's lack of clsact (above), one algorithm now exists decoupled from any particular capture method: `glitch/core` (`Engine`/`PacketMeta`/`Direction`) is `tc_glitch.bpf.c`'s logic ported to Go field-for-field (same adaptive EWMA baseline, TCP ACK gate, wraparound-safe sequence compare, stall episodes, UDP opt-in ports — see that package's own doc comments, which point back to the C file's comments as the authoritative explanation rather than re-deriving them), producing the exact same `glitch.Event`/`Kind` types the eBPF path already does. `glitch/afpacket` is a TPACKET_V3 AF_PACKET capture feeding that same `Engine` — the thing that actually works on WaveOS. Both are new code; **the existing eBPF path (`glitch/glitch.go`) is completely untouched**, so this phase carries zero risk to it. `cmd/glitch-tool`/`cmd/glitch-exporter` gained `-capture ebpf|afpacket` (default `ebpf`); `glitch_summary`/`glitch_event` gained an additive `capture` tag (see `metrics-endpoint.md`).

Implementation notes worth knowing:
- **`golang.org/x/sys/unix` only — no new dependency.** `gopacket`'s own `afpacket` package was tried first and rejected: its pinned release (`v1.1.19`) doesn't even build (`undefined: pageSize`, nothing in that package defines it) — a genuine upstream gap, not a config issue here. The classic BPF filter (kept TCP plus any opted-in UDP ports, truncate to 128 bytes) is hand-assembled via `golang.org/x/net/bpf` (already an indirect dependency, now direct) — unit-tested against its own software VM, no root needed, which is what made getting hand-written classic BPF (no named jump targets, only "skip N instructions" offsets) tractable at all.
- **Direction detection (`sll_pkttype`) required a live, byte-level investigation to get right, not just documentation.** For a TPACKET_V3 ring on a raw-IP interface (`wwan0`, same class as the WaveOS `lteN` interfaces), a populated `struct sockaddr_ll` — including `sll_pkttype`, exactly what distinguishes `PACKET_OUTGOING` from `PACKET_HOST` — sits at a fixed offset (`unix.SizeofTpacket3Hdr`, i.e. right after each packet's own `tpacket3_hdr`) within the ring frame, confirmed live via a raw byte dump on `aaeon`; it is **not** prepended to the captured packet bytes themselves the way a "cooked" capture's `recvfrom()`-facing data would carry it. The ring frame's own `mac`/`net` offset already points straight at the real IP header — this device has no link-layer header to skip (`mac == net`).
- **Flow-table bound, since fixed** — `glitch/core`'s flow map originally had no cap, unlike the kernel's own 10,000-entry `BPF_MAP_TYPE_LRU_HASH`. This was closed before Phase 3 (idle expiry, a 10,000-entry cap, and an evicted still-open episode reports `stall_abandoned` instead of silently disappearing) — see the bullet below for the commit.
- **`glitch/afpacket.Capture` has its own exclusivity lock** (`/run/glitch-afpacket-<iface>.lock`), deliberately separate from `glitch.Handle`'s own (`/run/glitch-<iface>.lock`) — the two capture backends must be able to run side by side on the same interface at once, which is the whole point of Phase 2's side-by-side comparison.
- **Verified live on `aaeon`'s `wwan0`**: a `glitch/afpacket`-only smoke test correctly parsed 108 real TCP packets with 0 drops (0 glitch events — the correct result for a healthy quiet window, not a sign of failure); `glitch-tool -capture afpacket` confirmed the full CLI wiring, including a clean shutdown (no hang — a real bug caught and fixed, same pattern as `gps/nmea.go`'s own shutdown-hang fix: a first version of the ring reader used a blocking read relying on another goroutine's `Close()` to unblock it, which doesn't reliably work here the same way it does for a `net.Conn`; rewritten to the same bounded `SetReadDeadline` pattern `gps/at.go`'s `drainPort` already uses).
- **AF_PACKET delivers packets in blocks, retired after at most `retireBlockTimeoutMs` (100ms) — this can delay when a `STALL_START` is *reported*, relative to eBPF, by up to that same ~100ms.** The kernel only hands a TPACKET_V3 block back to userspace once it's full or that timeout fires, so a packet that would trigger `glitch/core`'s `StallStart` can sit in a not-yet-retired block for up to 100ms before `glitch/afpacket`'s read loop ever sees it and feeds it to `Engine.HandlePacket` — the eBPF path has no equivalent delay (`egress_monitor` runs inline, synchronously, on the packet itself). **Event timestamps are unaffected** — `Event.Time` comes from the block's own per-packet `tpacket3_hdr` kernel timestamp (`Sec`/`Nsec`, taken when the packet actually arrived), not from when the read loop got around to processing it — so a duration/baseline computed from two events' `Time` fields is still accurate; only the wall-clock moment a consumer (`glitch-tool`'s printed line, `glitch-exporter`'s InfluxDB write) *learns about* a `StallStart` can lag by up to ~100ms versus the eBPF path. Worth knowing before a side-by-side comparison attributes a small timing difference to the algorithm instead of this.
- **Bounded flow table, done — required before Phase 3**, since a WaveOS `glitch-exporter` is meant to run unattended for weeks and the table was previously unbounded, unlike the kernel's own 10,000-entry LRU map. Idle expiry + 10,000-entry cap + `stall_abandoned` on eviction, confirmed in place (commit `9fb2eea`).
- **Real defect found and fixed via the simultaneous eBPF/AF_PACKET comparison: AF_PACKET could fragment one real outage into two reported episodes.** Confirmed genuinely simultaneous capture (both paths' first stall-triggering packet agreed to within ~65µs), then traced the disagreement to a specific mechanism: eBPF taps the clsact qdisc, before GSO segmentation, so one coalesced "send" is one packet to it; `glitch/afpacket` taps the wire, after GSO has split that same send into multiple segments microseconds apart. A second segment's near-zero gap satisfied `glitch/core`'s "not stalling" check and spuriously closed a stall episode it had just opened moments earlier — eBPF, seeing only the one coalesced packet, never had the chance to close early and reported one continuous episode instead. Step counts across AF_PACKET's two fragmented episodes summed to exactly the eBPF episode's own step count (3), confirming same underlying signal, different episode segmentation, not a different outcome. **Fixed in `glitch/core`**: a new `burstWindow` constant (1ms) — a packet arriving within it of the flow's previous packet is treated as the same logical send, skipping the stall-open/close decision and the EWMA update entirely for it (retransmission detection is unaffected, since it's independent and runs per segment regardless). `tc_glitch.bpf.c` has no equivalent and needs none — this situation cannot arise before GSO segmentation. Covered by `glitch/core/core_test.go`'s `TestEngine_BurstWindow_SameSendDoesNotSplitEpisode` (the exact sequence from the live run: trigger, same-burst segment, two retries, recovery — must yield one episode with 3 steps) and `TestEngine_BurstWindow_OrdinaryBulkTransfer_NoFalseStall` (confirms the skip doesn't itself introduce a false stall during ordinary GSO-split traffic). Verified fixed: eBPF/AF_PACKET episode durations and start times now match to within 0.0–0.1ms across 6 total simultaneous `test3b_simultaneous.sh` runs.
- **AF_PACKET drop investigation**: an early live run showed `glitch-tool`'s combined `Dropped()` at 562 during a ~1s congestion-recovery burst (`iperf3_retr≈2029`), with retrans counts suggesting AF_PACKET's own capture — not just the capture-point difference above — undercounts relative to iperf3's ground truth. `Dropped()` conflates two causally distinct things (`KernelDropped` — the kernel's `PACKET_STATISTICS` couldn't queue a packet into the ring at all, a real AF_PACKET capacity question relevant to Phase 3 sizing on WaveOS; `UserDropped` — this process's own 256-slot `Events()` channel wasn't drained fast enough, e.g. by `glitch-tool`'s synchronous one-`fmt.Printf`-per-event loop, a property of that particular consumer, not of capture/Engine), so the original 562 figure alone couldn't say which. Added `afpacket.Capture.KernelDropped()`/`UserDropped()` (outside the `Source` interface, since `glitch.Handle`'s own drop counting has no equivalent split) and `glitch-tool -capture afpacket` now prints the breakdown. Also added `UntruncatedOverLimit()`: counts ring packets whose `tp_len` (real on-wire length) exceeds the classic BPF filter's 128-byte `snapLen` but whose `tp_snaplen` equals `tp_len` anyway — i.e. the filter's own truncation (`RetConstant{Val: snapLen}` in `filter.go`) didn't take effect for them, which would mean full untruncated packets are consuming many times their expected ring footprint. **Result so far**: a fresh `test3b_simultaneous.sh` rerun (3 runs) showed `kernel=0 user=0 untruncated_over_limit=0` across all three — confirming the BPF filter's truncation genuinely works and no drops occurred under those bursts. Caveat: that rerun's bursts were smaller (`iperf3_retr` max 510) than the original 562-drop run (`iperf3_retr=2029`) — clean under moderate load, not yet proven at the largest-burst scale. The `2029 - 1467 = 562` exact match noted in an earlier pass is not being relied on as proof — drops plausibly include non-retransmitted packets too.
- **`bpf_src/test1_silence.sh`/`test2_loss.sh`/`test3_outage.sh`/`test3b_server_outage.sh`/`test3b_simultaneous.sh`** — Phase 2's side-by-side validation scripts (see each script's own header for its pass criteria). `test3_outage.sh` forces a short total outage via `netem loss 100%` on the gateway's own interface — valid for `-capture ebpf` only, since AF_PACKET observes egress after the qdisc and never sees the netem-dropped originals at all (see Hard Rules); `test3b_server_outage.sh` is valid for both, since its outage is a real `iptables` DROP on `wservices`, not anything injected at the gateway — but runs each capture method as its own separate invocation (own iperf3 connection, own SSH-triggered outage, at its own real time), which is sufficient to confirm each path detects a real outage on its own but not to say the two paths agree with each other on the identical packets (two separate TCP connections' own RTO-backoff timing relative to when the outage happens to land can genuinely differ by a whole backoff step — confirmed live, see "known limitations" below). **`test3b_simultaneous.sh`** closes that gap: it runs an eBPF and an AF_PACKET `glitch-tool` *at the same time*, watching one single iperf3 connection, scored against one single real outage trigger — using the two capture methods' independently-scoped exclusivity locks (`/run/glitch-<iface>.lock` vs `/run/glitch-afpacket-<iface>.lock`) to attach to the same interface simultaneously without contention. It additionally checks that both paths' one overlapping episode starts within 250ms of each other (AF_PACKET's documented ~100ms block-retire lag plus a safety margin — see the AF_PACKET latency note above) — a bigger gap on the *same real packets* is a real disagreement between the two detection paths, not timing jitter. **`sudo`-wrapping pitfall**: these scripts call `sudo` internally only where root is actually needed — wrapping the *whole script* in `sudo` changes `$HOME` to `/root` (breaking `test3b`'s SSH key lookup) and can cause `Permission Denied` on log files from a prior run; worse, a failed redirect on a *backgrounded* command doesn't trigger `set -e`, so the script can silently continue and report stale leftover data from old log files as if it were fresh. Always invoke these bare (`./bpf_src/test_x.sh`), never with a leading `sudo`.
  - **Pass criterion for `test3_outage.sh`/`test3b_server_outage.sh`/`test3b_simultaneous.sh` is "exactly one episode overlapping the outage's own wall-clock window" (episode start before the outage ends, episode end after it starts), duration > the outage length — not the weaker "at least one matching stall" used earlier.** That weaker form couldn't tell "one correctly-detected episode" apart from "the outage was wrongly split into two episodes, one of which happens to be long enough" — a real scoring gap, caught in review before Phase 3. A stall fully outside the outage window (a real cellular link can produce its own short, legitimate stall from ordinary jitter, unrelated to any injected outage — confirmed live) is still reported, just doesn't affect the verdict; two or more episodes *overlapping* the window is always a FAIL. Scored by **`bpf_src/score_outage.py`** (takes a glitch-tool log, the outage's own wall-clock window, and the outage length; parses each script's bracketing `date -u +%s.%N`/SSH-call timestamps against the window). This only works because **`cmd/glitch-tool/main.go`'s printed lines carry an RFC3339Nano UTC timestamp** (`ev.Time`, already wall-clock — see the `glitch.go`/`capture.go` doc comments on how each path derives it); previously each line carried only a relative gap/duration value, with no absolute time to compare against an outage window at all. Also: a `KindStallAbandoned` print case (glitch-tool used to silently drop this event type, even though `glitch/core`'s bounded flow table has produced it since the flow-table-bound commit).
  - **`test3b_server_outage.sh`/`test3b_simultaneous.sh` capture iperf3's own `Retr` total per run** (its sender-summary line, same `awk '/sender/{print $(NF-1)}'` technique `test2_loss.sh` already used) — cross-check against our own retrans count.
  - **`test3b`'s SSH key setup (`aaeon` → `wservices` as `idwave`, restricted to exactly two commands):** a dedicated `ed25519` key (`~/.ssh/id_ed25519_wservices_outage` on `aaeon`, no passphrase — it's invoked non-interactively) is restricted on the `wservices` side via a forced `command=` in `idwave`'s `authorized_keys`, pointing at a small dispatcher script (`~/bin/test3b-dispatch.sh` there) that only ever runs one of two hardcoded things regardless of what's actually asked: `sudo /usr/local/sbin/iperf-outage <seconds>` (the real outage, already covered by `idwave`'s own pre-existing `NOPASSWD` sudoers entry for that exact command) or `sudo /usr/sbin/iptables -S INPUT` (a read-only check for a leftover `dport 5201` rule, with its own `NOPASSWD` sudoers line — `idwave`'s only other sudo access is `(ALL:ALL) ALL`, which requires a password and so can't run non-interactively over this key at all). `no-agent-forwarding,no-port-forwarding,no-X11-forwarding,no-pty` on the `authorized_keys` line, same spirit as the dispatcher itself: this key can do exactly two things on `wservices`, nothing else, regardless of what anyone holding it asks for.

**Two BPF programs, one shared `flow_tracker` LRU-hash map (10k flows, keyed by 5-tuple):**
- `egress_monitor` (clsact **egress** hook, `TC_H_MIN_EGRESS = 0xFFF3`) does the real work: per-flow inter-packet-gap pacing (EWMA), stall-episode tracking, and TCP sequence tracking for retransmission detection.
- `ingress_monitor` (clsact **ingress** hook, `TC_H_MIN_INGRESS = 0xFFF2`) only tracks the highest TCP ACK number the remote peer has sent back per flow, so `egress_monitor` can tell "stuck with real data in flight" apart from "idle, nothing queued" — see the TCP stall gate below. It looks up existing `flow_tracker` entries only, never creates one; `egress_monitor` is the sole owner of a flow's lifecycle.

**⚠️ Historical bug, now fixed, worth knowing if you ever see old captured output:** the constant originally used for "egress" (`main.go`'s `HANDLE_MINEGRESS`, carried over verbatim into `glitch/glitch.go` during the Phase 1 extraction) was `0xFFF2` — which is actually `TC_H_MIN_INGRESS` in the real kernel/netlink ABI, not egress. Every result measured against that code — `dawn-agent`'s own output, the original (pre-refactor) stress test, and this project's early Phase 2 review findings — was therefore observing **ingress (downlink)** traffic, not egress (uplink), regardless of what it was labeled as at the time. Fixed in commit `023a517`; `glitch/glitch.go`'s `handleMinEgress`/`handleMinIngress` constants now use the correct values, each with a comment explaining the swap.

**⚠️ Second historical bug, also fixed:** `highest_ack` was seeded at a bare `0` instead of the flow's own first packet's seq (see below) — since TCP ISNs are randomized across the full 32-bit range, this silently disabled TCP stall detection for roughly half of all connections (whichever half happened to land at or above 2³¹), which looked exactly like cwnd/timing-dependent test flakiness until traced to the real cause. Fixed in commit `e1b0945`; after the fix, a repeated forced-outage test that previously passed only 2 of 5 runs passed 10 of 10.

**Stall episodes, not one event per lagging packet.** A single real outage often produces several TCP RTO retries at growing backoff intervals (e.g. 140ms, 270ms, 550ms, 1.1s) — reporting each as its own event would read as a burst of unrelated stalls instead of the one underlying problem. Instead: the first gap exceeding a flow's adaptive baseline emits `EVENT_TYPE_STALL_START` (`glitch.KindStallStart`) immediately — needed for a closed-loop reaction, so it can't wait for the episode to end — every qualifying gap after that silently extends the open episode (a step counter, no event), and the first normal-paced gap closes it with `EVENT_TYPE_STALL_END` (`glitch.KindStallEnd`), carrying the **total duration** (from the last good packet before the episode to the packet that closed it) and the **step count** (how many qualifying gaps were folded in — matches the visible retry count).

**Adaptive baseline, not a fixed threshold.** A gap only counts as "qualifying" once it exceeds `max(100ms floor, 4 × that flow's own EWMA of its recent inter-packet gaps)`, and only after the flow has seen at least 8 packets (`STALL_MIN_PACKETS`) — long enough for the EWMA to be representative. This is what lets a flow with its own slow, legitimate pace (a 1s/100ms keepalive, even with jitter) go unflagged, while a genuinely stalled bulk flow (whose normal pace is far below 100ms) still trips the fixed floor. A gap that triggers a stall step is never folded into the EWMA itself — folding it in would drag the baseline upward right when it most needs to stay representative of the flow's *normal* pace.

**TCP stall eligibility is additionally gated on real outstanding data**, not just a big gap: `egress_monitor` only counts a gap toward a stall once `end_seq` (the furthest byte offset sent so far) is strictly ahead of `highest_ack` (the highest ACK `ingress_monitor` has seen for that flow) — i.e. there's genuinely unacknowledged data in flight. An idle TCP connection with nothing queued to send is never flagged just for going quiet.
- **`highest_ack` is seeded from the flow's own first packet's seq when the entry is created, not from a bare 0.** TCP ISNs are randomized across the full 32-bit range, so roughly half of all connections have seq/ack values that sit at or above 2³¹ for their entire practical lifetime (real transfer sizes never approach the 4 GiB wrap). With a 0 origin, `(s32)(real_ack - 0)` is always negative for those connections, so `ingress_monitor`'s "did the ack advance" check never saw an advance and `highest_ack` stayed stuck at 0 forever — and independently, `egress_monitor`'s own eligibility check also came out negative, purely because `end_seq` itself was ≥ 2³¹. Net effect: stall detection was **permanently disabled for ~50% of TCP flows**, which looked exactly like cwnd/timing-dependent test flakiness until traced to the real cause (fixed in commit `e1b0945`; `bpf_src/verify_highest_ack_wraparound.sh` is a synthetic `bpftool prog run` regression test for it, since it needs sequence numbers ≥ 2³¹ to reproduce — ordinary live traffic only hits that region about half the time).

**UDP gets no stall detection by default.** There's no ACK signal for UDP, so there's no way to tell "stuck" apart from "application has nothing queued" the way the TCP gate above does. A port (checked against either side of a flow) can opt in via the `UDP_MONITOR_PORTS` array in `bpf_src/tc_glitch.bpf.c` — a fixed-size, **load-time constant** (empty by default; editing it means rebuilding, not a runtime config option).

**Retransmission detection** is independent of the stall-episode logic above and unaffected by any of its gating: a TCP segment whose `seq` is behind the flow's `end_seq` (wraparound-safe signed-difference compare, same idiom the Linux kernel's own TCP stack uses) and which carries real payload (`payload_len > 0`, so a pure ACK/keepalive resending the same seq by design never counts) emits `EVENT_TYPE_RETRANS` (`glitch.KindRetrans`) — fires regardless of pacing, and regardless of whether a stall episode is simultaneously open.

**Known limitations, inherent to this design (not bugs to fix, but real boundaries to know about):**
- **Stalls are detected when the silence ends, not while it lasts** — `STALL_END` (and the episode's final step count/duration) is only known once a normal-paced packet arrives, so there is no way to report "still stalling, N seconds so far" mid-outage from the kernel side alone. (`glitch-exporter`'s `stall_abandoned` handles the case where no such packet ever arrives — see the `telemetry-schema` skill — but that is a 30s timeout giving up, not a mid-outage progress report.)
- **An outage shorter than the time the sender needs to exhaust its congestion window (roughly one RTT) can leave no egress gap at all.** If the sender still has enough already-queued, already-sent-but-unacked data to keep transmitting new segments throughout a short outage, egress pacing never actually goes quiet — the connection's own stream of data packets continues uninterrupted, just all getting lost downstream. The only visible signal for that case is the retransmission burst once the link recovers, not a stall episode.
- **A TCP stall episode's reported duration includes retransmission-timer backoff**, which roughly doubles on each retry (RFC 6298-style exponential backoff) — so a episode spanning 3-4 RTO retries can report a duration on the order of **2× the underlying outage**, not a 1:1 measurement of how long the network was actually down. The step count is what tells these apart from a single long gap.
- **UDP stall ports are fixed at compile time and empty by default** (see `UDP_MONITOR_PORTS` above) — no UDP flow is stall-checked at all unless `bpf_src/tc_glitch.bpf.c` is edited and rebuilt.
