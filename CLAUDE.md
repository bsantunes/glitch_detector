# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

DAWN6G glitch detector: started as a single eBPF-powered 5G gateway agent (`dawn-agent`), now split into four shared packages (`modem/`, `twamp/`, `gps/`, `glitch/`) plus consumers — `cmd/modem-tool`/`cmd/twamp-tool`/`cmd/gps-tool`/`cmd/glitch-tool` (standalone diagnostic CLIs), and `cmd/modem-exporter`/`cmd/twamp-exporter`/`cmd/gps-exporter`/`cmd/glitch-exporter` (long-running InfluxDB/Grafana telemetry push). **`dawn-agent` (the original single-binary eBPF + TWAMP + modem metrics agent, Debian/ModemManager gateways only) is superseded by `glitch-exporter` + `twamp-exporter` + `modem-exporter` running side by side** — kept in the tree, not deleted, but no longer built/installed by default and no longer safe to trust as-is (see the `glitch/` package section — its own BPF loading is frozen on a pre-refactor struct layout that no longer matches what the shared `tc_glitch.o` object now emits). **Builds and runs only on Linux** (eBPF, netlink, mmcli/qmicli/uqmi/ubus), not on macOS.

Two gateway OS targets exist in the fleet:
- **Debian** (e.g. host `aaeon`) — SIMCom modem via ModemManager, runs the full `dawn-agent` (eBPF works here).
- **WaveOS** (OpenWrt-based, x86_64 Supermicro boards, e.g. hosts `6global`/`dawn6g`) — **confirmed to lack `clsact`/TC-BPF kernel support** (kernel 5.15.167, `netlink.QdiscAdd` fails with ENOENT; `modprobe cls_bpf`/`sch_ingress` also fail). The whole eBPF path (`dawn-agent`, `glitch-tool`, `glitch-exporter`) cannot run there — only `modem-tool`/`modem-exporter`/`twamp-tool`/`twamp-exporter`/`gps-exporter` are deployed on WaveOS boards. `gps-exporter` is deployed and running there via the AT-over-serial backend (confirmed live, sustained, zero real errors); `gps-tool` itself is built/unit-tested but not installed as a running service anywhere — see the `gps/` package section and Deployment Context.

## Repository Layout

- `main.go` → `dawn-agent` binary — eBPF passive detection + TWAMP + modem status line (Debian gateways only). **Superseded** — see Project Overview and the `glitch/` package section; kept in the tree, no longer built/installed by default, and its own BPF event decoding is stale against the current shared `tc_glitch.o`.
- `glitch/` — shared package: loads `bpf_src/tc_glitch.bpf.c`'s two eBPF programs (`egress_monitor`/`ingress_monitor`), tracks per-flow stall episodes and TCP retransmissions, decodes ring-buffer events into a clean `Event` type. Has unit tests (`go test ./glitch/...`) for the wire-format decode only — the BPF program's own logic is validated via `bpf_src/verify_highest_ack_wraparound.sh` and manual `bpftool prog run`/live-traffic testing (needs root + real hardware), not `go test`. See the `glitch/` package section below.

## `glitch/` package

eBPF passive monitor: detects TCP retransmissions and reports stall episodes on an interface's egress path, gated so an idle connection is never mistaken for a stuck one. `glitch.Open(iface)` loads `bpf_src/tc_glitch.bpf.c`'s compiled object (embedded via `go:embed`, so `glitch/tc_glitch.o` must exist at compile time — `make embed`/`make glitch/tc_glitch.o` before a bare `go vet`/`go test`), attaches **two** eBPF programs on the same `clsact` qdisc, and decodes its ring-buffer events into a clean `Event{Time, SrcIP, DstIP, SrcPort, DstPort, Value, Baseline, Type, Steps, Proto}`.

**Two BPF programs, one shared `flow_tracker` LRU-hash map (10k flows, keyed by 5-tuple):**
- `egress_monitor` (clsact **egress** hook, `TC_H_MIN_EGRESS = 0xFFF3`) does the real work: per-flow inter-packet-gap pacing (EWMA), stall-episode tracking, and TCP sequence tracking for retransmission detection.
- `ingress_monitor` (clsact **ingress** hook, `TC_H_MIN_INGRESS = 0xFFF2`) only tracks the highest TCP ACK number the remote peer has sent back per flow, so `egress_monitor` can tell "stuck with real data in flight" apart from "idle, nothing queued" — see the TCP stall gate below. It looks up existing `flow_tracker` entries only, never creates one; `egress_monitor` is the sole owner of a flow's lifecycle.

**⚠️ Historical bug, now fixed, worth knowing if you ever see old captured output:** the constant originally used for "egress" (`main.go`'s `HANDLE_MINEGRESS`, carried over verbatim into `glitch/glitch.go` during the Phase 1 extraction) was `0xFFF2` — which is actually `TC_H_MIN_INGRESS` in the real kernel/netlink ABI, not egress. Every result measured against that code — `dawn-agent`'s own output, the original (pre-refactor) stress test, and this project's early Phase 2 review findings — was therefore observing **ingress (downlink)** traffic, not egress (uplink), regardless of what it was labeled as at the time. Fixed in commit `023a517`; `glitch/glitch.go`'s `handleMinEgress`/`handleMinIngress` constants now use the correct values, each with a comment explaining the swap.

**⚠️ Second historical bug, also fixed:** `highest_ack` was seeded at a bare `0` instead of the flow's own first packet's seq (see below) — since TCP ISNs are randomized across the full 32-bit range, this silently disabled TCP stall detection for roughly half of all connections (whichever half happened to land at or above 2³¹), which looked exactly like cwnd/timing-dependent test flakiness until traced to the real cause. Fixed in commit `e1b0945`; after the fix, a repeated forced-outage test that previously passed only 2 of 5 runs passed 10 of 10.

**Stall episodes, not one event per lagging packet.** A single real outage often produces several TCP RTO retries at growing backoff intervals (e.g. 140ms, 270ms, 550ms, 1.1s) — reporting each as its own event would read as a burst of unrelated stalls instead of the one underlying problem. Instead: the first gap exceeding a flow's adaptive baseline emits `EVENT_TYPE_STALL_START` (`glitch.KindStallStart`) immediately — needed for a closed-loop reaction, so it can't wait for the episode to end — every qualifying gap after that silently extends the open episode (a step counter, no event), and the first normal-paced gap closes it with `EVENT_TYPE_STALL_END` (`glitch.KindStallEnd`), carrying the **total duration** (from the last good packet before the episode to the packet that closed it) and the **step count** (how many qualifying gaps were folded in — matches the visible retry count).

**Adaptive baseline, not a fixed threshold.** A gap only counts as "qualifying" once it exceeds `max(100ms floor, 4 × that flow's own EWMA of its recent inter-packet gaps)`, and only after the flow has seen at least 8 packets (`STALL_MIN_PACKETS`) — long enough for the EWMA to be representative. This is what lets a flow with its own slow, legitimate pace (a 1s/100ms keepalive, even with jitter) go unflagged, while a genuinely stalled bulk flow (whose normal pace is far below 100ms) still trips the fixed floor. A gap that triggers a stall step is never folded into the EWMA itself — folding it in would drag the baseline upward right when it most needs to stay representative of the flow's *normal* pace.

**TCP stall eligibility is additionally gated on real outstanding data**, not just a big gap: `egress_monitor` only counts a gap toward a stall once `end_seq` (the furthest byte offset sent so far) is strictly ahead of `highest_ack` (the highest ACK `ingress_monitor` has seen for that flow) — i.e. there's genuinely unacknowledged data in flight. An idle TCP connection with nothing queued to send is never flagged just for going quiet.
- **`highest_ack` is seeded from the flow's own first packet's seq when the entry is created, not from a bare 0.** TCP ISNs are randomized across the full 32-bit range, so roughly half of all connections have seq/ack values that sit at or above 2³¹ for their entire practical lifetime (real transfer sizes never approach the 4 GiB wrap). With a 0 origin, `(s32)(real_ack - 0)` is always negative for those connections, so `ingress_monitor`'s "did the ack advance" check never saw an advance and `highest_ack` stayed stuck at 0 forever — and independently, `egress_monitor`'s own eligibility check also came out negative, purely because `end_seq` itself was ≥ 2³¹. Net effect: stall detection was **permanently disabled for ~50% of TCP flows**, which looked exactly like cwnd/timing-dependent test flakiness until traced to the real cause (fixed in commit `e1b0945`; `bpf_src/verify_highest_ack_wraparound.sh` is a synthetic `bpftool prog run` regression test for it, since it needs sequence numbers ≥ 2³¹ to reproduce — ordinary live traffic only hits that region about half the time).

**UDP gets no stall detection by default.** There's no ACK signal for UDP, so there's no way to tell "stuck" apart from "application has nothing queued" the way the TCP gate above does. A port (checked against either side of a flow) can opt in via the `UDP_MONITOR_PORTS` array in `bpf_src/tc_glitch.bpf.c` — a fixed-size, **load-time constant** (empty by default; editing it means rebuilding, not a runtime config option).

**Retransmission detection** is independent of the stall-episode logic above and unaffected by any of its gating: a TCP segment whose `seq` is behind the flow's `end_seq` (wraparound-safe signed-difference compare, same idiom the Linux kernel's own TCP stack uses) and which carries real payload (`payload_len > 0`, so a pure ACK/keepalive resending the same seq by design never counts) emits `EVENT_TYPE_RETRANS` (`glitch.KindRetrans`) — fires regardless of pacing, and regardless of whether a stall episode is simultaneously open.

**Known limitations, inherent to this design (not bugs to fix, but real boundaries to know about):**
- **Stalls are detected when the silence ends, not while it lasts** — `STALL_END` (and the episode's final step count/duration) is only known once a normal-paced packet arrives, so there is no way to report "still stalling, N seconds so far" mid-outage from the kernel side alone. (`glitch-exporter`'s `stall_abandoned` handles the case where no such packet ever arrives — see its own section below — but that is a 30s timeout giving up, not a mid-outage progress report.)
- **An outage shorter than the time the sender needs to exhaust its congestion window (roughly one RTT) can leave no egress gap at all.** If the sender still has enough already-queued, already-sent-but-unacked data to keep transmitting new segments throughout a short outage, egress pacing never actually goes quiet — the connection's own stream of data packets continues uninterrupted, just all getting lost downstream. The only visible signal for that case is the retransmission burst once the link recovers, not a stall episode.
- **A TCP stall episode's reported duration includes retransmission-timer backoff**, which roughly doubles on each retry (RFC 6298-style exponential backoff) — so a episode spanning 3-4 RTO retries can report a duration on the order of **2× the underlying outage**, not a 1:1 measurement of how long the network was actually down. The step count is what tells these apart from a single long gap.
- **UDP stall ports are fixed at compile time and empty by default** (see `UDP_MONITOR_PORTS` above) — no UDP flow is stall-checked at all unless `bpf_src/tc_glitch.bpf.c` is edited and rebuilt.

See the `glitch-exporter` entry under Telemety below for `glitch_summary`/`glitch_event`'s InfluxDB schema, and `metrics-endpoint.md` for the authoritative field-by-field reference.

## `modem/` package

Hybrid detection cascade, each tried in order until one finds a modem: **ModemManager → `ubus` (WaveOS's own `qmi` object) → QMI (`qmicli`)/MBIM → `uqmi` → AT-over-serial**. `ubus` is tried before raw QMI/`uqmi` specifically to avoid QMI client-ID exhaustion when running alongside WaveOS's own `uqmi-ubus` daemon (see Known Issues).

- `Signal{Technology, Role, RSRP, RSRQ, RSSI, SINR}` — `Role` is `"anchor"` or `"scg"`. `GetSignals()` returns one `Signal` per simultaneously active radio leg (EN-DC: LTE anchor + NR secondary, confirmed live on `aaeon`); `GetSignal()` is a convenience wrapper returning just the anchor leg. Only ModemManager and QMI (`qmicli`) can currently report >1 leg.
- `CellInfo{PLMN, OperatorName, RegistrationState, PacketServiceState, TAC, CellID}` — TAC/CellID normalized to **decimal** across backends, except the `ubus` backend, which currently passes Quectel's raw **hex** TAC/CellID straight through unconverted (known bug, not yet fixed — flagged but deferred).
- **A modem with no SIM can still report real RSRP/RSRQ/RSSI/SINR/PLMN/TAC/CellID** by camping on a cell's broadcast system information (physical-layer, unauthenticated) — it just can never complete registration/attach (no IMSI to authenticate with). Confirmed live on `6global`. Don't assume "no SIM" implies "no data."
- `SupportsCellInfo(method)` — only ModemManager/`ubus`/QMI/`uqmi` implement `GetCellInfo`; MBIM/AT don't yet (no real hardware to validate against).

## `twamp/` package

Native Go sender for "TWAMP Light" (RFC 5357-style, unauthenticated, no TWAMP-Control handshake — direct UDP TWAMP-Test packets). `Measure(ctx, reflectorAddr, count, probeInterval, timeout) (Result, error)` sends a burst of packets and computes `Result{Sent, Received, AvgRTT, Jitter, LossPct}`.

**Packet sizes deliberately diverge from RFC 5357's stated minimums** (`senderPacketLen = 14`, `reflectedHeaderLen = 38`, not the RFC's 41/41) — found via live `strace -f -e trace=network` on `twampy` itself, which showed the real deployed reflector (`10.30.30.1:862`) expects/sends packets smaller than the RFC minimums. This is intentional: it matches the actual wire behavior of this project's reflector, not the spec. If TWAMP is ever pointed at a different reflector and gets 100% loss, check packet sizes via `strace` again before assuming the sizes are wrong.

Confirmed live with 0% loss against `10.30.30.1:862` from `aaeon`, `6global`, and `dawn6g`.

**The reflector itself** (`10.30.30.1:862`) is `wservices.wavesys.pt` — the same box that hosts the InfluxDB/Grafana stack (`dawn6g-metrics/`), just reached over the private `10.30.30.x` VPN overlay instead of its public domain. It runs `twampy` (a third-party Python TWAMP implementation, **not** this repo's own `twamp/`/`twamp-tool`, which are the client/sender side only) in `responder` mode, installed in a venv at `/home/idwave/twampy/venv`. **Run it as `twampy-responder.service`** (tracked in this repo, reference copy — deploy by copying to `/etc/systemd/system/` on `wservices` and `systemctl enable --now twampy-responder`), not by hand in a terminal — a manually-backgrounded (`sudo ... &`) run is fragile and **has already gone silently stopped (`T` state) once** when its controlling SSH session ended, with no indication other than every gateway's TWAMP reads silently starting to show 100% loss. The systemd service survives reboots/updates and auto-restarts on crash.

## `gps/` package

Reads GPS/GNSS fixes from a modem's own GNSS receiver. Deliberately a standalone package (own process, `gps-tool`/`gps-exporter`) — not wired into `dawn-agent`'s active-monitoring loop or folded into `modem/`'s stateless per-call backend shape, because the QMI backend genuinely needs a different shape (see below).

**Fleet-wide status**: `gps-exporter` runs cleanly on `6global`/`dawn6g` via AT-over-serial (confirmed live, sustained, zero real errors) — no fix on either board yet, since neither has a GPS antenna connected (only the cellular antenna is known-good on those two). **`aaeon` is different: it has a working GNSS antenna.** Manual AT-over-serial testing on `aaeon` (outside `gps-exporter`, which remains stopped/disabled there — see the incident below) tracked real GPS satellites (04/27/28/31) and GLONASS (83) at 25-35 dB-Hz and obtained a valid fix: `$GPRMC,192721.00,A,4132.984808,N,00824.784113,...`, decoding to **41.549747, -8.413069** (Portugal) — this is now the reference fix for later testing. The earlier "no antenna" theory for `aaeon`'s ModemManager `GeneralError` (below) is therefore **disproven**: the antenna works, the receiver tracks satellites and fixes fine over AT; whatever causes ModemManager's own enable call to fail is a separate, unknown issue that is deliberately not being investigated — see that bullet. **`aaeon`'s `gps-exporter` service itself is still stopped/disabled**, independent of this finding — re-enabling it via the AT backend on a dedicated reserved port is now mid-flight: the port is reserved and validated (Phase C, below), and a supervised live test (Phase D) is the remaining gate before flipping the service over.

**⚠️ Third incident, this one on `aaeon` (production Debian gateway) — `gps-exporter` is stopped+disabled there, not running:**
1. `aaeon`'s GPS-engine-enable (`mmcli --location-enable-gps-raw`) had already failed earlier with a `GeneralError` of unknown cause — the antenna is confirmed working (see the ModemManager bullet below) — `gps-exporter` was still deployed and left polling every 30s regardless, since a failed enable isn't fatal by design (same as every other backend).
2. Those repeated `--location-get` polls started failing with `modem has no location capabilities`, then — after ModemManager picked up a PolicyKit rule change (see below) — with `Unauthorized: PolicyKit authorization failed: not authorized for 'org.freedesktop.ModemManager1.Location'`. A new rule, `/etc/polkit-1/rules.d/49-modemmanager-location-root.rules`, was added to grant root that action explicitly (ModemManager's default policy requires `allow_active`, which doesn't cleanly apply to a non-interactive root systemd service — no rules.d files existed on this box at all before this one).
3. A `sudo systemctl restart ModemManager` (tried to force it to re-probe location capabilities) triggered `[/dev/cdc-wdm0] endpoint hangup` / `fatal error initializing: modem is unusable` during ModemManager's own internal QMI version-info handshake — **the same corruption signature as the two `6global` incidents**, but this time via ModemManager's own internal QMI client, not raw `qmicli`, and on a third distinct modem (this board's SIMCom). `ModemManager` has shown `No modems were found` ever since.
4. **Production impact was real but limited, not an outage**: `modem-exporter`'s own cascade fell through to its raw-QMI fallback during the window ModemManager had no modem (the already-documented startup-race behavior, just self-triggered this time) — confirmed via live InfluxDB queries that real signal/registration data kept flowing the whole time via that fallback. Best-guess cause: `modem-exporter`'s raw-QMI fallback client and ModemManager's own reinitializing client raced for the same physical QMI channel on `/dev/cdc-wdm0` at the same moment — the same *class* of contention the `ubus`-priority design already exists to avoid on WaveOS, just not something this Debian board's architecture has an equivalent guard against.
5. Decision (matching the `6global` incidents' handling): leave `ModemManager` as-is rather than force another restart attempt — production data is flowing fine via the fallback, so there's no urgency, and repeated recovery attempts are exactly what's caused escalation twice already this session. `gps-exporter` was stopped and disabled on `aaeon` (`sudo systemctl stop gps-exporter && sudo systemctl disable gps-exporter`) so it can't repeat this pattern on a future reboot. **Don't re-enable it there, and don't attempt another `ModemManager` restart/reinit, without a real plan** — same spirit as the QMI-backend disable above, now extended to ModemManager's Location interface specifically on this board.

**Phase C (reserving a dedicated AT port for GPS) — done on `aaeon`.** A udev rule reserves the SIMCom's secondary AT port (ModemManager's `AT_SECONDARY` role — its primary AT port, `AT_PRIMARY`, was deliberately *not* chosen, since that one isn't safe to take away from ModemManager) exclusively for GPS, matched by vendor/product ID plus USB interface number rather than by `ttyUSB` index (which can shift across boots/kernel versions): `/etc/udev/rules.d/99-dawn-gps.rules` —
```
SUBSYSTEM=="tty", ATTRS{idVendor}=="1e0e", ATTRS{idProduct}=="9001", ENV{ID_USB_INTERFACE_NUM}=="03", ENV{ID_MM_PORT_IGNORE}="1", SYMLINK+="dawn-gps"
```
`ID_MM_PORT_IGNORE=1` is the same property ModemManager's own shipped rules use to mean "never touch this port" — and the same property `modem.DetectAT`'s AT fallback now skips (commit `1ee26b6`, added specifically so `modem-exporter`'s AT fallback and `gps-exporter` could never fight over this port; confirmed first that `modem-exporter` on `aaeon` uses ModemManager, never AT, so this was a defense-in-depth fix, not one closing a live collision). Validated with `udevadm test` (dry run) before rebooting: `ttyUSB3` matched (`ID_MM_PORT_IGNORE=1` set, `dawn-gps` symlink added), `ttyUSB2` (the primary AT port) matched neither. After the reboot: `ttyUSB3` shows as `ignored` in `mmcli`'s own port list, `/dev/dawn-gps` → `ttyUSB3`, `fuser` confirms no process holds it, and `wwan0`/`modem-exporter`/`twamp-exporter`/`glitch-exporter` all stayed up and connected straight through the reboot. A manual `AT+CGPSXE?` over `/dev/dawn-gps` afterward confirmed XTRA assistance data (enabled by hand earlier this session) **persists across a reboot** — it's stored in the modem, not reset per-session, which matters for Phase D's cold-start comparison below. Rollback, if ever needed: `sudo rm /etc/udev/rules.d/99-dawn-gps.rules && sudo udevadm control --reload-rules && sudo reboot`. Full procedure (rule, dry-run validation, post-reboot checks, rollback) is in `DEPLOYMENT.md`.

`Supports(method)` — **ModemManager and AT-over-serial are enabled; raw QMI is deliberately disabled**:
- **ModemManager**: `gps-raw` location source reports already-parsed decimal `modem.location.gps.{latitude,longitude,altitude}` directly — no NMEA parsing needed. Enabled via `--location-enable-gps-raw` (root/PolicyKit-gated, retried the same way `modem/mmcli.go`'s `runMmcliSetup` does). **On `aaeon`, enabling it fails**: `sudo mmcli -m 0 --location-enable-gps-raw` →
  ```
  error: couldn't setup location gathering: 'GDBus.Error:org.freedesktop.ModemManager1.Error.MobileEquipment.PhoneFailure:
  QMI protocol error: Couldn't enable location 'gps-raw' gathering: Couldn't start GPS engine: QMI protocol error (46): 'GeneralError''
  ```
  **This was previously theorized as a missing GPS antenna on `aaeon` — that theory is now disproven.** Manual AT-over-serial testing (see "Fleet-wide status" above) confirmed `aaeon` has a working GNSS antenna: real satellites tracked at 25-35 dB-Hz and a valid fix obtained. The real cause of this `GeneralError` is **unknown and deliberately not being investigated** — candidates include the GNSS engine already being started over AT when ModemManager's own QMI-based enable runs, the modem's firmware expecting a different QMI location service than the one ModemManager targets, or QMI client contention (the same general class of issue documented elsewhere in this section) — but the AT-over-serial backend below avoids ModemManager's location interface entirely, making this moot for `aaeon`'s actual GPS path going forward. Per this project's hard constraints: **never call `mmcli --location-*` on `aaeon`, and never restart ModemManager there** (see the incident writeup below for why that specifically is dangerous on this board). The ModemManager code path itself remains implemented and otherwise ready; it's just not the backend `aaeon` will use.
- **AT-over-serial (`gps/at.go`) — confirmed live, sustained, zero errors on `6global` and `dawn6g` (no fix — no antenna on either board, same as every other backend there).** SIMCom (`AT+CGPS=1,1`/`AT+CGPSINFO`) and Quectel (`AT+QGPS=1`/`AT+QGPSLOC=2`); both enable their GNSS engine and poll cleanly. **On `aaeon`'s SIMCom modem, manual testing this session (run by hand over the AT port, outside `gps-exporter` itself) got a real fix** — but only after also enabling SIMCom's XTRA assistance data (`AT+CGPSXE=1`), which the engine doesn't request on its own: with `AT+CGPS=1,1` alone, the receiver tracked real satellites (25-35 dB-Hz) but never resolved a position; with XTRA also enabled, `AT+CGPSINFO` returned a valid fix within a reasonable wait. **`gps/at.go`'s enable sequence does not do this yet** — it starts the GNSS engine but never enables XTRA, so a deployed `gps-exporter` would currently see the same no-fix behavior this manual test saw before XTRA was added by hand. Wiring XTRA into the enable sequence is tracked as separate follow-up work, not done yet. `modem.PortInUse` (scans `/proc/*/fd`) makes `DetectAT` skip any serial port another process already has open — specifically written to avoid the kind of port collision that caused the QMI incidents below, since WaveOS's `uqmi-ubus` daemon holds its own AT ports open continuously for PCI/EARFCN polling. Two real bugs surfaced and fixed via this live testing, both in shared `modem/at.go` (so they also improve `modem.Detect()`'s own AT fallback, not just `gps/`): `parseATI` was misreading a Quectel's unsolicited `+CPIN: NOT INSERTED` spam (arriving before its actual `ATI` reply) as the manufacturer/model string; and the enable retry loop was treating "GNSS already running" (SIMCom: plain `ERROR`; Quectel: `+CME ERROR: 504`) as a failure to retry past, rather than querying the vendor's own state command and accepting confirmed-already-on as success. **One thing still not confirmed**: Quectel's `AT+QGPSLOC=2` reports lat/lon as signed decimal degrees per its documentation, including a community-reported longitude sign bug on some firmware — unverified either way; `aaeon`'s real fix was from a SIMCom modem (different reply format, `AT+CGPSINFO`'s ddmm.mmmm/hemisphere style, not Quectel's signed-decimal `AT+QGPSLOC=2`), so it doesn't settle the Quectel-specific question — no Quectel board has gotten a real fix yet to check against a known reference point.
- **Raw QMI (`qmicli`) is implemented but deliberately disabled** (`Supports`/`NewPoller` both refuse it — see ⚠️ below). The code (`QMISession`) is real and was confirmed working against a SIMCom modem (real NMEA sentences streaming, no fix — no antenna), but is gated off after repeatedly corrupting production QMI client state — see the incident writeup below before ever re-enabling it.
- `ubus`/`uqmi` are **not implemented**: `ubus`'s `"location"` method only returns cell-ID/LAC-CI data, never real GPS coordinates, despite the name (would need a patch to the vendor's `uqmi-ubus.lua` — assessed as feasible in principle, since it already runs `AT+QENG` for PCI/EARFCN and discards those too, but not attempted); `uqmi` lists `pds` as a service name but exposes no actual PDS/location CLI action.

**`gps.Detect`/`gps-tool`/`gps-exporter` do NOT reuse `modem.Detect()`'s cascade result** — that cascade prioritizes `ubus` over raw QMI specifically to avoid QMI client contention, but `ubus` has no GPS support at all, so naively using its pick means they'd find nothing on any WaveOS board. Instead `gps.Detect` tries ModemManager, then raw QMI/MBIM, then AT — but unlike `modem.Detect()`, it doesn't stop at the first step that finds *any* modem, only at the first step that finds one `Supports` will actually use (`anySupported`). That distinction matters on WaveOS specifically: raw `qmicli` reliably answers `cdc-wdm0`/`cdc-wdm1` (so a naive "first non-empty result wins" cascade would stop there), but every modem QMI finds is currently unusable for GPS (disabled) — without the `anySupported` check, AT would never be reached at all.

**⚠️ Raw QMI backend disabled after two separate production incidents this session — read before touching `Supports`/`NewQMISession`:**
1. **First incident**: manually killing `qmicli --loc-follow-nmea` with `timeout` (SIGTERM, but `qmicli` doesn't release its QMI client cleanly on it) against `6global`'s Quectel (`/dev/cdc-wdm1`) left its QMI control endpoint hung (`CID allocation failed... endpoint hangup`) for *every* process on that device node, not just the one killed — this also broke the production `uqmi-ubus` daemon's own access to that modem, taking down `modem-exporter`'s telemetry for it. Restarting `qmi-proxy`/`uqmi-ubus` did **not** recover it; only a board reboot did.
2. **`QMISession.Close()` was fixed** to call `--loc-stop` first (letting `--loc-follow-nmea` exit on its own) and only force-kill as a timeout fallback, specifically to prevent a repeat.
3. **Second incident, despite that fix**: a single, clean `gps-exporter` test run against `6global` (SIMCom, `/dev/cdc-wdm0`, no abrupt kill involved — session ended via the new graceful `Close()` path) still left that device's raw QMI client state corrupted afterward (`CID allocation failed... Service mismatch`), confirmed moments later and still broken after a short wait (not a transient race). Production (`ubus`-based `modem-exporter`) was **not** affected this second time, but direct `qmicli` access to that device was.

**Root cause, with a concrete candidate fix found via research (not yet tried live):** `qmicli` gives every separate invocation (`--loc-start`, `--loc-follow-nmea`, `--loc-stop`) its own throwaway client ID (CID), auto-released on exit — but LOC's start/follow/stop is meant to be *one* session spanning three processes, which libqmi mailing-list threads describing this identical symptom say requires explicitly carrying one CID across all three via `--client-cid=N --client-no-release-cid`. Our original code let each step grab its own anonymous CID, so `--loc-stop` was very plausibly stopping a different, irrelevant client than the one `--loc-follow-nmea` actually held — meaning it could never cleanly end *that* process's session regardless of the graceful-`Close()` fix, explaining why the fix didn't prevent the second incident. Medium-high confidence in this diagnosis (well-supported by multiple independent upstream threads with the identical pattern and fix), but **not verified against our actual incident** — desk research, not a confirmed root-cause analysis. Key sources: [libqmi#38](https://gitlab.freedesktop.org/mobile-broadband/libqmi/-/issues/38), [libqmi-devel: QMI LOC improvements (2018)](https://lists.freedesktop.org/archives/libqmi-devel/2018-July/002916.html), [libqmi-devel: CID leak consultation (2021)](https://lists.freedesktop.org/archives/modemmanager-devel/2021-December/009055.html).

Since AT-over-serial now works and makes QMI unnecessary for GPS on these boards, **there's no pressing need to re-enable or test this fix** — but if QMI GPS is ever revisited, rewriting `QMISession` to hold one CID across `--loc-start`/`--loc-follow-nmea`/`--loc-stop` (instead of letting each grab its own) is the single most actionable thing to try first, and should still be tested very conservatively (one controlled session, not repeated cycling) before trusting it in production again. **Do not re-enable `Supports(modem.MethodQMI)` or call `NewQMISession` against `6global`/`dawn6g` without that fix and a real plan for the remaining risk.**

## Architecture

Full two-endpoint component diagram (gateway + server), including the current `glitch/`/`glitch-tool`/`glitch-exporter` pipeline: see `ARCHITECTURE.md`. The rest of this section describes `dawn-agent`'s own, **superseded and frozen** pipeline specifically — see the `glitch/` package section above for the current architecture (two BPF programs, stall episodes, ACK-gating), which `dawn-agent`'s own loading code does not use or benefit from.

1. **Kernel space — `bpf_src/tc_glitch.bpf.c`** (Debian gateways only, shared with `glitch/` — there is only one BPF source file): TC egress program (`egress_monitor`). `dawn-agent`'s own Go decode logic still assumes the pre-refactor 24-byte `glitch_event` layout (no ports, a plain `last_ts`/`max_seq` struct, a single fixed 100ms threshold) — it was never updated alongside the `glitch/` package's Phase 1-3 work, so it no longer matches what the shared, currently-compiled `tc_glitch.o` actually emits (48-byte struct, episodes, ACK-gated stalls). Don't trust `dawn-agent`'s stall/retrans output as anything other than historical reference.

2. **User space — `main.go`**: loads `tc_glitch.o` via cilium/ebpf, adds a `clsact` qdisc and attaches the program as a filter via vishvananda/netlink using a `HANDLE_MINEGRESS = 0xFFF2` constant that **is actually `TC_H_MIN_INGRESS`, not egress** — see the `glitch/` package section's "Historical bug" note. `dawn-agent` itself was never fixed (it's frozen/superseded), so this misattachment is still present in its own code today, on top of the struct-layout mismatch above. Runs two loops:
   - **Passive**: reads `GlitchEvent`s from the ring buffer and prints them (🔴 loss / ⚠️ stall) — unreliably, given both issues above.
   - **Active** (`runActiveMonitoring`, every 5s): calls `modem.Detect`/`modem.GetSignal`/`modem.GetCellInfo` for radio status, and `twamp.Measure` (native Go sender, `twamp/` package — no longer shells out to `twampy`/Python) for RTT/jitter/loss. This half is unaffected by the eBPF issues above and still works.

**Struct layout coupling**: Go's `GlitchEvent` (main.go) must match the C `glitch_event` (tc_glitch.bpf.c) field-for-field — events are decoded with `binary.Read` little-endian. (`glitch/glitch.go`'s own `wireEvent` is the up-to-date equivalent for the current struct layout.)

## Telemetry (InfluxDB/Grafana)

**Read `metrics-endpoint.md` first** — it's the authoritative handoff doc, written for Claude Code specifically, and its target schema matches what's actually implemented (unlike the `.docx`/`dawn6g-metrics/README.md`, which describe an earlier, superseded draft — see Repository Layout).

The real server stack is **`~/dawn6g-metrics` on `wservices.wavesys.pt`** (Apache on the host, not Docker, is the sole public entry point and also serves Nagios — never take port 443 from it; InfluxDB/Grafana are Docker Compose, bound to loopback only). This repo's own `docker-compose.yml` is stale/unrelated (wrong org/bucket names, no TLS) — ignore it. Org `wavecom`; buckets `radio` (90d, modem signal/cell telemetry), `network` (90d, now live — TWAMP RTT/jitter/loss and `glitch-exporter`'s stall/retransmission stats, see below; still earmarked for future QoS/nDPI data too), `events` (365d, unused so far — future event-driven RadioEvent points), **`location`** (365d, added this session — device GPS/GNSS position, see below; deliberately its own bucket rather than folded into `radio`, since GPS isn't a radio metric despite coming from the same modem hardware).

**What `modem-exporter` writes today** (confirmed live on `aaeon`/`6global`/`dawn6g`, to `radio` only) — this matches `metrics-endpoint.md`'s target schema exactly, except `pci` (optional there, not implemented — see Known Issues):
- `radio_cell`: tags `device`/`modem_id`/`method`/`rat`/`role` (+`plmn`/`tac` on anchor rows only); fields `rsrp`/`rsrq`/`rssi`/`sinr` (NaN-omitted) + `cell_id` (anchor rows only).
- `modem_state`: tags `device`/`modem_id`; fields `operator_name`/`registration_state`/`packet_service_state`.
- Uses `WriteAPIBlocking` + log-and-drop on failure (deliberate: avoids unbounded in-RAM buffering on constrained devices if InfluxDB is unreachable). Both `metrics-endpoint.md` and the `.docx`/README recommend the retry-buffered async `WriteAPI` (batch 500, flush 1000ms, 10 retries, 100k-point RAM buffer) instead — a real, repeatedly-suggested tradeoff worth reconsidering, not just a one-off idea.
- `metrics-endpoint.md`'s "TODO 1" (migrate off the old `modem_telemetry`/`device_id` schema) is **done** as of this session. Its "TODO 2" (provision the Grafana dashboard as JSON under `dawn6g-metrics/grafana/provisioning/dashboards/`) is **still open** — a dashboard exists and works in Grafana's live DB, but isn't captured as repo-tracked JSON yet (now also true of a TWAMP panel/dashboard, not yet added — see below), so none of it survives the Grafana container's volume being lost/recreated. Datasource UID is `influxdb-flux` (Flux query language, default bucket `radio`).

**What `twamp-exporter` writes** (confirmed live on `aaeon`/`6global`/`dawn6g`, to `network`) — schema is new, not specified by `metrics-endpoint.md` (which only earmarks the bucket, not a schema):
- `twamp`: tags `device`/`reflector`; fields `rtt_ms`/`jitter_ms`/`loss_pct` (floats) + `sent`/`received` (ints), one point per probe burst (default interval 30s).
- Same `WriteAPIBlocking` + log-and-drop pattern as `modem-exporter`, same reasoning.
- **A Grafana panel for this now exists** (built live in Grafana's UI this session — not yet repo-tracked JSON, same open "TODO 2" gap as the `radio` dashboard). Query:
  ```flux
  from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "twamp")
    |> filter(fn: (r) => r._field == "rtt_ms" or r._field == "jitter_ms" or r._field == "loss_pct")
    |> filter(fn: (r) => r.device =~ /^${device:regex}$/)
  ```
  Reuses the dashboard's existing `device` template variable (query: `tagValues(bucket: "network", tag: "device")`, multi-value on) — `:regex` formatting is what makes multi-select/"All" work with `=~`, since plain `==` only matches one value. Same `influxdb-flux` datasource as the `radio` panels, just pointed at the `network` bucket.

**What `glitch-exporter` writes** (confirmed live on `aaeon` — a test-3-style forced outage's `glitch_summary`/`glitch_event` points matched the kernel's own reported duration/steps exactly, and 10+ minutes of background-only traffic kept ticking `glitch_summary` with `stall_episodes=0` throughout; see the `glitch/` package section above for the detection logic this schema reports on), to `network`:
- `glitch_summary`: one point per `-interval` (default 10s), **always written even when every field is zero** — a heartbeat, unlike every other exporter's "skip if nothing to report" convention. Tags: `device`/`iface`. Fields: `stall_episodes` (int, count of `STALL_END`s this interval), `stall_max_ms`/`stall_sum_ms` (float, ms), `stall_open` (int, episodes started but not yet ended as of this point — a live snapshot, not an interval accumulator), `retrans_count` (int), `dropped_events` (uint, the delta of `glitch.Handle.Dropped()` since the last tick).
- `glitch_event`: one point per `stall_start`/`stall_end`/`stall_abandoned` — never for a retransmission, which is counted only, via `glitch_summary.retrans_count`. Timestamped with the kernel event's own time (or, for `stall_abandoned`, the moment the 30s timeout was detected — there is no kernel event to read a time from for one). Tags: `device`/`iface`/`type`. Fields: `proto` (int), `src_port`/`dst_port` (int), `dst_ip` (string — **never a tag**, see below), `baseline_ms` (float), and — `stall_end`/`stall_abandoned` only — `duration_ms` (float) and `steps` (int, always 0 for `stall_abandoned`: the kernel only reports a step count on `STALL_END`, which by definition never arrived for an abandoned episode, so the real count is genuinely unknown, not a plausible-looking default). Rate-limited to `-max-events-per-sec` (default 20) points/second, shared across all three types — anything over the limit still counts in `glitch_summary`.
- **Deliberately never tags on an IP address or port anywhere** in this schema — unlike `radio_cell`'s `device`/`modem_id` or `twamp`'s `reflector`, a 5-tuple is high-cardinality and per-flow, not a stable grouping key; `dst_ip`/`src_port`/`dst_port` live only on `glitch_event`'s fields.
- `stall_abandoned`: if a connection dies mid-outage, `STALL_END` never arrives and the kernel-side episode state is lost with it. `glitch-exporter`'s own `Aggregator.CheckAbandoned` (run every 5s, independent of `-interval`) gives up on an open episode after 30s with no `STALL_END`, reports it with the duration measured so far, and drops it from the open set — it does **not** count toward `glitch_summary.stall_episodes`/`stall_max_ms`/`stall_sum_ms`, which are literal `STALL_END`s only.
- Uses the async, batching `WriteAPI` (not `WriteAPIBlocking`, unlike every other exporter here) — deliberate, since the ring-buffer reader must never block on InfluxDB.
- **Known gotcha, not a bug**: on `aaeon`, `glitch-exporter`'s own InfluxDB write traffic goes out over the same `wwan0` interface it's monitoring (no split-tunnel/separate management interface), so its own HTTPS writes are themselves counted in whatever stats it reports — a brief InfluxDB-direction hiccup can show up as a tiny, legitimate blip in its own numbers, not a sign the detector is wrong.
- No Grafana panel for this yet — same open "TODO 2"-style gap as `radio`/`twamp`'s own dashboards (see above), not yet captured as repo-tracked JSON.

**What `gps-exporter` writes** (schema confirmed suitable, but no real `gps_fix` point has actually landed in InfluxDB yet — `aaeon` obtained a real fix manually over AT, but its exporter isn't reading that path yet; see `gps/` package section): measurement `gps_fix` in the `location` bucket. Tags `device`/`modem_id`/`method`; fields `latitude`/`longitude`/`altitude` (floats). **Only written when `Fix.Valid == true`** — skip the point entirely otherwise, same "return nil, don't write" pattern `radioCellPoint`/`modemStatePoint` already use, but for a different reason: `(0, 0)` is a real coordinate (Null Island), so unlike signal metrics there's no safe NaN-style sentinel for "no fix yet." Deliberately a **separate bucket**, not folded into `radio` — plan is to **join at query time** (Flux `join()` on the `device` tag against the latest `gps_fix` point) for map panels combining radio/network metrics with position, rather than denormalizing lat/lon onto every `radio_cell`/`twamp` point.

**Per-device tokens**: `./add-device.sh <id>` in `dawn6g-metrics/` on `wservices` — writes `secrets/devices/<id>.token` **and** `secrets/devices/<id>.authid` (the InfluxDB auth entry's own ID; `revoke-device.sh` needs this file and can't revoke by token value alone). `aaeon`/`6global`/`dawn6g` all have proper `.authid` files as of this session (`6global`/`dawn6g`'s earlier manually-created tokens, which lacked one, were rotated out — see below). **No in-place way to add a permission to an existing token** — this InfluxDB CLI's `auth` command only supports `create`/`delete`/`active`/`inactive`, no `update`; expanding a token's bucket scope means issuing a new one and rotating it in (create new → deploy → verify → revoke old — never revoke-then-recreate, to avoid a write-gap window).
On each gateway, the token is wired in as `INFLUX_TOKEN` — `/opt/dawn/modem-exporter.env` (mode 600) for systemd, baked into the `procd` init script for WaveOS. This diverges from `metrics-endpoint.md`'s documented on-device convention (`/etc/dawn6g/influx.token`, read directly as a file by the Go agent) — functionally fine since our services resolve the env var themselves, but worth knowing if anything else ever expects that exact path.
**All three device tokens, plus Grafana's read-only token, were rotated this session** to add `location`-bucket access (`add-device.sh`/`bootstrap.sh` now provision/scope all four buckets for new tokens automatically). One gotcha hit during the Grafana token rotation: a Docker Compose file-based secret is mounted into the container with the **exact host file permissions/ownership**, not normalized — `chmod 600`-ing the secret file (seemed like better hygiene) broke Grafana's ability to read it (its container runs as a different UID than the host file owner), surfacing as `provisioning: open /run/secrets/...: permission denied`. Match the original file's mode (`644`) when touching these secret files, don't tighten them.
**Known cleanup opportunity, not yet done**: a stale, pre-`add-device.sh` token literally named `dawn6g` (not `device:dawn6g`), write-scoped to `radio` only, is still sitting unrevoked in InfluxDB (`influx auth list` will show it) — it predates this repo's current token conventions and isn't used by anything live, but hasn't been cleaned up.

**Known deployed devices**: `aaeon` (Debian, ModemManager, SIMCom, real MEO registration), `6global` (WaveOS Supermicro, reachable at `10.10.10.184`, SIMCom + Quectel), `dawn6g` (WaveOS Supermicro, `10.10.10.201`, SIMCom + Quectel). Neither WaveOS board has an antenna connected. `6global` has no SIM; its Quectel has nonetheless shown real RSRP/PLMN/TAC (see the no-SIM note above) by camping on a nearby cell through incidental RF leakage on the bare antenna connector — not reproducible/meaningful until a real antenna is attached. **`dawn6g` got a real SIM installed this session (2026-11-10)** — its Quectel (`lte1`) registered immediately with operator NOS over `ubus`, confirming the SIM/registration path works end-to-end; still no antenna attached.

## Known Issues

- **Startup detection race, no retry on the `ubus`/QMI cascade.** `modem.Detect()` runs once per process lifetime. If WaveOS's `uqmi-ubus` daemon (or ModemManager) isn't fully ready yet right after a reboot, detection falls through to a worse/contention-prone method (raw `qmicli`/`uqmi`) and never re-evaluates — this has caused real QMI client-ID exhaustion in production (`6global`, twice). A retry-with-backoff exists for ModemManager's `--signal-setup` call specifically (`modem/mmcli.go`, `runMmcliSetup`) but **not** for the overall cascade. If telemetry goes quiet after a reboot, check whether the process is stuck on `qmicli`/`uqmi` (log lines say `via: QMI`/`via: uqmi` instead of `via: ubus`/`via: ModemManager`) and just restart the service — a fresh detection pass usually fixes it immediately.
- **`uqmi-ubus.lua` discards PCI/EARFCN/bandwidth.** It computes them via `AT+QENG` (Quectel) but explicitly nils them before exposing anything over `ubus` (`/lib/wavesys/lib/lua/uqmi/uqmi-ubus.lua`). Not fixable from this repo — would need a patch to that vendor script.
- **`ubus` backend doesn't normalize TAC/CellID to decimal** (see above) — cosmetic inconsistency vs. other backends, not yet fixed.
- **QMI's location/LOC subsystem can corrupt QMI client state (`endpoint hangup`) for reasons not yet fully understood, across more than one access path.** Three separate incidents this session: twice on `6global` via raw `qmicli` LOC sessions (disabling `gps/`'s raw-QMI backend as a result — see that package's section), and once on `aaeon` via **ModemManager's own internal QMI client** while its Location interface was being exercised repeatedly, unrelated to raw `qmicli` misuse this time. `gps-exporter` is stopped/disabled on `aaeon` as a result — see the `gps/` package section's incident writeup before re-enabling GPS there or attempting another `ModemManager` restart on that board.

## Deployment Context

- `dawn-agent.service`: systemd unit; runs `init_gateway.sh` first, then the agent from `/opt/dawn`. **Superseded** — not installed on `aaeon` (`systemctl is-enabled dawn-agent` → `not-found`); `glitch-exporter.service` + `twamp-exporter.service` + `modem-exporter.service` cover what it used to do.
- `glitch-exporter.service`: **installed, enabled, and running on `aaeon`** (confirmed survives a reboot). `Conflicts=dawn-agent.service`. No OpenWrt deployment — the eBPF side doesn't run on WaveOS at all.
- `init_gateway.sh`: loads kernel modules, configures the modem's dedicated QoS bearer via AT commands (DSCP EF / cid 2), and sets up HTB traffic shaping with a priority lane for EF-marked traffic.
- `modem-tool.service`/`modem-exporter.service`/`twamp-tool.service`/`twamp-exporter.service`: systemd units for the Debian gateway; `openwrt/*.init` for WaveOS (`procd`). All four are deployed and running on `aaeon`/`6global`/`dawn6g` as of this session.
- `gps-exporter.service`/`openwrt/gps-exporter.init`: **`gps-exporter` is deployed and running on `6global`/`dawn6g`** (procd, AT-over-serial backend, both modems detected cleanly on each board, no real errors). **On `aaeon` it's installed but stopped and disabled** after the ModemManager incident below — don't re-enable it there without a real plan. No real `gps_fix` points land anywhere yet — `6global`/`dawn6g` have no GPS antenna; `aaeon` has one, but its `gps-exporter` is disabled there pending Phase D (Phase C — reserving `/dev/dawn-gps` for GPS — is done; see the `gps/` package section). `gps-tool.service`/`openwrt/gps-tool.init` are built/unit-tested but not installed anywhere — `gps-exporter` alone was deployed, since nothing needs the local-journalctl-only tool running continuously alongside it (see the `modem-tool`/`modem-exporter` redundancy note in `DEPLOYMENT.md`).
