# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Hard Rules

- **Never call `mmcli --location-*` on `aaeon`, and never restart ModemManager there** — both have corrupted its QMI client state in the past (see the `gps-integration` skill's incident writeup).
- **Never re-enable the raw QMI GPS backend** (`gps.Supports(modem.MethodQMI)` / `NewQMISession`) — disabled after repeated production QMI-corruption incidents on `6global` and `aaeon` (see the `gps-integration` skill).
- **Never edit files directly in `~/glitch_detector` on `aaeon`** — that checkout is a deploy target, not a dev workspace; `git commit`/`push`/`pull` only there, develop elsewhere.
- **`dawn6g` is the priority device; `6global` is deliberately switched off; `aaeon` is the backup/test bed** — don't treat `6global`'s silence in InfluxDB as an incident, and don't propose bring-up work for it unless asked.
- **`bpf_src/test3_outage.sh`'s netem-induced outage is valid for `-capture ebpf` only** — AF_PACKET never sees the netem-dropped originals. Use `test3b_simultaneous.sh` to compare the two capture paths against each other.
- **Ask before making any production change on `dawn6g`** — it carries live customer traffic (Quectel on `lte1`/`mwan1`).

## Project Overview

DAWN6G glitch detector: started as a single eBPF-powered 5G gateway agent (`dawn-agent`), now split into four shared packages (`modem/`, `twamp/`, `gps/`, `glitch/`) plus consumers — `cmd/modem-tool`/`cmd/twamp-tool`/`cmd/gps-tool`/`cmd/glitch-tool` (standalone diagnostic CLIs), and `cmd/modem-exporter`/`cmd/twamp-exporter`/`cmd/gps-exporter`/`cmd/glitch-exporter` (long-running InfluxDB/Grafana telemetry push). **`dawn-agent` (the original single-binary eBPF + TWAMP + modem metrics agent, Debian/ModemManager gateways only) is superseded by `glitch-exporter` + `twamp-exporter` + `modem-exporter` running side by side** — kept in the tree, not deleted, but no longer built/installed by default and no longer safe to trust as-is (see the `glitch-detector-internals` skill — its own BPF loading is frozen on a pre-refactor struct layout that no longer matches what the shared `tc_glitch.o` object now emits). **Builds and runs only on Linux** (eBPF, netlink, mmcli/qmicli/uqmi/ubus), not on macOS.

Two gateway OS targets exist in the fleet:
- **Debian** (e.g. host `aaeon`) — SIMCom modem via ModemManager, runs the full `dawn-agent` (eBPF works here).
- **WaveOS** (OpenWrt-based, x86_64 Supermicro boards, hosts `6global`/`dawn6g`) — confirmed to lack `clsact`/TC-BPF kernel support (kernel 5.15.167, `netlink.QdiscAdd` fails with ENOENT; `modprobe cls_bpf`/`sch_ingress` also fail) — see the `glitch-detector-internals` skill's WaveOS feasibility notes. Until/unless that changes, only `modem-tool`/`modem-exporter`/`twamp-tool`/`twamp-exporter`/`gps-exporter` are deployed on WaveOS boards. **`tc` itself (the whole binary, not just clsact/TC-BPF) is also confirmed absent on `dawn6g`** (`which tc` → exit 1) — `bpf_src/test2_loss.sh`'s netem-based loss injection (`test_common.sh`'s `add_netem`) cannot run there as written; skip test2 on WaveOS boards, test1/test3/test3b don't need `tc`. `gps-exporter` is deployed and running there via the AT-over-serial backend; `gps-tool` itself is built/unit-tested but not installed as a running service anywhere — see the `gps-integration` skill and Deployment Context below.

## Repository Layout

- `main.go` → `dawn-agent` binary — eBPF passive detection + TWAMP + modem status line (Debian gateways only). **Superseded** — see Project Overview and the `glitch-detector-internals` skill; kept in the tree, no longer built/installed by default, and its own BPF event decoding is stale against the current shared `tc_glitch.o`.
- `glitch/` — shared package: loads `bpf_src/tc_glitch.bpf.c`'s two eBPF programs (`egress_monitor`/`ingress_monitor`), tracks per-flow stall episodes and TCP retransmissions, decodes ring-buffer events into a clean `Event` type. Has unit tests (`go test ./glitch/...`) for the wire-format decode only — the BPF program's own logic is validated via `bpf_src/verify_highest_ack_wraparound.sh` and manual `bpftool prog run`/live-traffic testing (needs root + real hardware), not `go test`. See the `glitch-detector-internals` skill.
- `cmd/glitch-tool/` → `glitch-tool` binary — attach, print stall/retransmission events to stdout forever. No InfluxDB. Mirrors `modem-tool`/`twamp-tool`/`gps-tool`'s structure.
- `cmd/glitch-exporter/` → `glitch-exporter` binary — attach, aggregate stall episodes + retransmission counts, push to InfluxDB's `network` bucket on an interval. Meant to run as a service, not interactively. Its aggregation logic (`cmd/glitch-exporter/aggregate.go`) is pure and clock-injectable specifically so `cmd/glitch-exporter/aggregate_test.go` can cover it (summary rollup, rate limiting, abandoned-episode timeout) without root, eBPF, or a real InfluxDB.
- `modem/` — shared package: hybrid modem detection + signal/cell-info reading. Has unit tests (`go test ./modem/...`), several built from real captured `mmcli`/`qmicli`/`uqmi`/`ubus` output. See the `modem-detection` skill.
- `cmd/modem-tool/` → `modem-tool` binary — detect modems, then poll and print signal+cell info forever. No InfluxDB, no eBPF. See `MODEM_TOOL.md`.
- `cmd/modem-exporter/` → `modem-exporter` binary — detect modems, then push signal+cell info to InfluxDB on an interval. Meant to run as a service, not interactively.
- `twamp/` — shared package: native Go TWAMP-Light sender (no external `twampy`/Python dependency — required for WaveOS, which has no Python at all). Has unit tests (`go test ./twamp/...`). See the `twamp-measurement` skill.
- `cmd/twamp-tool/` → `twamp-tool` binary — probe a TWAMP-Test reflector on an interval and print RTT/jitter/loss forever. No InfluxDB. Mirrors `modem-tool`'s structure.
- `cmd/twamp-exporter/` → `twamp-exporter` binary — probe a TWAMP-Test reflector, then push RTT/jitter/loss to InfluxDB's `network` bucket on an interval. Mirrors `modem-exporter`'s structure; reuses the same per-device token file.
- `gps/` — shared package: GPS/GNSS fix reading via ModemManager's `gps-raw` location source, AT-over-serial (vendor-specific commands), or raw QMI's LOC service (implemented, deliberately disabled — see Hard Rules and the `gps-integration` skill). Deliberately its own package, not folded into `modem/` — see the `gps-integration` skill for why. Has unit tests (`go test ./gps/...`).
- `cmd/gps-tool/` → `gps-tool` binary — probe for a GPS fix on an interval and print it forever. No InfluxDB. Mirrors `modem-tool`/`twamp-tool`'s structure.
- `cmd/gps-exporter/` → `gps-exporter` binary — probe for a GPS fix, then push it to InfluxDB's `location` bucket on an interval (only when a fix is actually valid). Mirrors `modem-exporter`/`twamp-exporter`'s structure; reuses the same per-device token file. Only usable where `gps.Supports` is true — currently ModemManager and AT-over-serial (raw QMI is implemented but deliberately disabled; see the `gps-integration` skill).
- `openwrt/*.init` — `procd` init scripts for WaveOS (`modem-tool.init`, `modem-exporter.init`, `twamp-tool.init`, `twamp-exporter.init`, `gps-tool.init`, `gps-exporter.init`, `glitch-exporter.init`; the exporter ones need their `DEVICE_ID`/token edited per board before install). `gps-exporter.init` is actually deployed on WaveOS (see above); `gps-tool.init` is not installed anywhere. `glitch-exporter.init` (Phase 3) always runs `-capture afpacket` — the eBPF path doesn't exist on WaveOS at all.
- `*.service` — `systemd` units for Debian gateways (`dawn-agent.service`, `modem-tool.service`, `modem-exporter.service`, `twamp-tool.service`, `twamp-exporter.service`, `gps-tool.service`, `gps-exporter.service`, `glitch-exporter.service`). Plus `twampy-responder.service` — **not a gateway unit**, a reference copy of the TWAMP reflector's own service, which runs on `wservices.wavesys.pt`, not any gateway — see the `twamp-measurement` skill. `glitch-exporter.service` sets `Conflicts=dawn-agent.service` — both would otherwise try to attach their own eBPF program to the same interface. ## Build & Run

See the `Makefile` for all build/install targets (`make`, `make <tool>-tool`, `make <tool>-exporter`, `sudo make install-<tool>`, `sudo make install`) and each `main.go`/`cmd/*/main.go`'s `flag.String` calls for runtime flags (e.g. `-iface`, `-reflector`, `-capture`). Both `dawn-agent` and `glitch-tool` need root to load eBPF.

On WaveOS: no Go/clang toolchain on-device and storage is tight — cross-compile `CGO_ENABLED=0` elsewhere (static binary, no libc to match) and copy just the binary + an `openwrt/*.init` script over. See `MODEM_TOOL.md`'s WaveOS section for the full walkthrough (`twamp-tool`/`twamp-exporter` follow the identical pattern — same `GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build`).

**On `aaeon`, the on-device dev/build checkout is `~/glitch_detector`, not `~/glitch_detector_dev`** — the latter predates this repo's git history reaching that board (discovered when a `git pull` there failed with `fatal: not a git repository`; it was a plain file-transfer target, not a clone) and is left as-is, untouched, until the services actually installed from it are rebuilt from the real clone. Don't build, test, or run `make install` from `~/glitch_detector_dev` going forward (see also Hard Rules on not editing `~/glitch_detector` directly). A proper versioned-deploy path (`/opt/dawn/src`, tagged releases, so "what commit is this board actually running" stops depending on which directory someone happened to build in) is tracked as separate future work alongside the device-ID/versioning effort, not done yet.

Notes:
- **`go.mod`/`go.sum` are committed and pinned, not generated at build time.** Before this was fixed, they were gitignored and the Makefile ran `go mod init`/`go get` on every fresh checkout — meaning a build on a new board (or after `make clean`'s equivalent of wiping them) could silently pick up newer dependency versions than any previously-tested build, and did: confirmed live on `aaeon`, where a fresh resolution pulled `cilium/ebpf v0.22.0` and that in turn forced a `go1.26` toolchain auto-download, on top of whatever `go1.24`/`go1.25.x` toolchains earlier builds had already pulled — real non-reproducibility, not a theoretical concern. Fixed by generating `go.mod`/`go.sum` once from a known-good `aaeon` build, committing them, dropping `*.mod`/`*.sum` from `.gitignore`, and replacing the Makefile's `go mod init`/`go get`/`deps` steps with plain `go build` (which now just uses the committed, already-resolved module graph). To intentionally update a dependency, run `go get <module>@<version>` (or `go get -u` for everything) and commit the resulting `go.mod`/`go.sum` diff deliberately — never let it happen as a side effect of an unrelated build.
- The `go 1.25.0` directive at the top of `go.mod` (a three-component version, not just `go 1.25`) already pins the exact toolchain `go build` uses, the same thing an explicit `toolchain go1.25.0` line would do here — tried adding one anyway and `go build -mod=mod` pruned it right back out as redundant/untidy, since a three-component `go` line already serves that purpose. Nothing else in this module's locked dependency graph needs anything newer, confirmed by a from-scratch `go build ./...`/`go vet ./...`/`go test ./...` run against the committed `go.mod`/`go.sum` with no changes to either file.
- `dawn-agent` loads `tc_glitch.o` from the current working directory at runtime; `glitch/` instead embeds `glitch/tc_glitch.o` at compile time via `go:embed` (see the `glitch-detector-internals` skill) — run `make embed`/`make glitch/tc_glitch.o` before a bare `go vet ./...`/`go test ./...` on a fresh checkout, or package `glitch` won't even compile.
- `modem/`, `twamp/`, `gps/`, and `glitch/` all have real unit tests; `dawn-agent`'s eBPF side still has none (`stress_test.sh` / `tc qdisc ... netem` for manual validation). The BPF program's own logic (as opposed to `glitch/`'s Go-side wire decode) is validated via `bpf_src/verify_highest_ack_wraparound.sh` and manual `bpftool prog run`/live-traffic testing instead, since it needs root and real hardware — not something `go test` can exercise.

## Architecture

Full two-endpoint component diagram (gateway + server), including the current `glitch/`/`glitch-tool`/`glitch-exporter` pipeline: see `ARCHITECTURE.md`. The rest of this section describes `dawn-agent`'s own, **superseded and frozen** pipeline specifically — see the `glitch-detector-internals` skill for the current architecture (two BPF programs, stall episodes, ACK-gating), which `dawn-agent`'s own loading code does not use or benefit from.

1. **Kernel space — `bpf_src/tc_glitch.bpf.c`** (Debian gateways only, shared with `glitch/` — there is only one BPF source file): TC egress program (`egress_monitor`). `dawn-agent`'s own Go decode logic still assumes the pre-refactor 24-byte `glitch_event` layout (no ports, a plain `last_ts`/`max_seq` struct, a single fixed 100ms threshold) — it was never updated alongside the `glitch/` package's Phase 1-3 work, so it no longer matches what the shared, currently-compiled `tc_glitch.o` actually emits (48-byte struct, episodes, ACK-gated stalls). Don't trust `dawn-agent`'s stall/retrans output as anything other than historical reference.

2. **User space — `main.go`**: loads `tc_glitch.o` via cilium/ebpf, adds a `clsact` qdisc and attaches the program as a filter via vishvananda/netlink using a `HANDLE_MINEGRESS = 0xFFF2` constant that **is actually `TC_H_MIN_INGRESS`, not egress** — see the `glitch-detector-internals` skill's "Historical bug" note. `dawn-agent` itself was never fixed (it's frozen/superseded), so this misattachment is still present in its own code today, on top of the struct-layout mismatch above. Runs two loops:
   - **Passive**: reads `GlitchEvent`s from the ring buffer and prints them (🔴 loss / ⚠️ stall) — unreliably, given both issues above.
   - **Active** (`runActiveMonitoring`, every 5s): calls `modem.Detect`/`modem.GetSignal`/`modem.GetCellInfo` for radio status, and `twamp.Measure` (native Go sender, `twamp/` package — no longer shells out to `twampy`/Python) for RTT/jitter/loss. This half is unaffected by the eBPF issues above and still works.

**Struct layout coupling**: Go's `GlitchEvent` (main.go) must match the C `glitch_event` (tc_glitch.bpf.c) field-for-field — events are decoded with `binary.Read` little-endian. (`glitch/glitch.go`'s own `wireEvent` is the up-to-date equivalent for the current struct layout.)

## Known Issues

- **Startup detection race, no retry on the `ubus`/QMI cascade.** `modem.Detect()` runs once per process lifetime. If WaveOS's `uqmi-ubus` daemon (or ModemManager) isn't fully ready yet right after a reboot, detection falls through to a worse/contention-prone method (raw `qmicli`/`uqmi`) and never re-evaluates — this has caused real QMI client-ID exhaustion in production (`6global`, twice). A retry-with-backoff exists for ModemManager's `--signal-setup` call specifically (`modem/mmcli.go`, `runMmcliSetup`) but **not** for the overall cascade. If telemetry goes quiet after a reboot, check whether the process is stuck on `qmicli`/`uqmi` (log lines say `via: QMI`/`via: uqmi` instead of `via: ubus`/`via: ModemManager`) and just restart the service — a fresh detection pass usually fixes it immediately.
- **`uqmi-ubus.lua` discards PCI/EARFCN/bandwidth.** It computes them via `AT+QENG` (Quectel) but explicitly nils them before exposing anything over `ubus` (`/lib/wavesys/lib/lua/uqmi/uqmi-ubus.lua`). Not fixable from this repo — would need a patch to that vendor script.
- **`ubus` backend doesn't normalize TAC/CellID to decimal** (see above) — cosmetic inconsistency vs. other backends, not yet fixed.
- **QMI's location/LOC subsystem can corrupt QMI client state (`endpoint hangup`) for reasons not yet fully understood, across more than one access path.** Three separate incidents: twice on `6global` via raw `qmicli` LOC sessions (disabling the raw-QMI GPS backend as a result — see the `gps-integration` skill), and once on `aaeon` via **ModemManager's own internal QMI client** while its Location interface was being exercised repeatedly, unrelated to raw `qmicli` misuse that time. `gps-exporter` is stopped/disabled on `aaeon` as a result — see the `gps-integration` skill's incident writeup before re-enabling GPS there or attempting another `ModemManager` restart on that board (see also Hard Rules).

## Deployment Context

- `dawn-agent.service`: systemd unit; runs `init_gateway.sh` first, then the agent from `/opt/dawn`. **Superseded** — not installed on `aaeon` (`systemctl is-enabled dawn-agent` → `not-found`); `glitch-exporter.service` + `twamp-exporter.service` + `modem-exporter.service` cover what it used to do.
- `glitch-exporter.service`: **installed, enabled, and running on `aaeon`** (confirmed survives a reboot). `Conflicts=dawn-agent.service`. No OpenWrt deployment — the eBPF side doesn't run on WaveOS at all.
- `init_gateway.sh`: loads kernel modules, configures the modem's dedicated QoS bearer via AT commands (DSCP EF / cid 2), and sets up HTB traffic shaping with a priority lane for EF-marked traffic.
- `modem-tool.service`/`modem-exporter.service`/`twamp-tool.service`/`twamp-exporter.service`: systemd units for the Debian gateway; `openwrt/*.init` for WaveOS (`procd`). All four are deployed and running on `aaeon`/`6global`/`dawn6g`.
- `gps-exporter.service`/`openwrt/gps-exporter.init`: **`gps-exporter` is deployed and running on `6global`/`dawn6g`** (procd, AT-over-serial backend, both modems detected cleanly on each board, no real errors) **and now also on `aaeon`** (systemd, `-method at -port /dev/dawn-gps`, Phase C/D — see the `gps-integration` skill), superseding the earlier stopped/disabled state there. No real `gps_fix` points have landed in InfluxDB from a running exporter yet: `6global` has no antenna on either modem; `aaeon`'s manual-AT fix was outside `gps-exporter` itself; `dawn6g`'s Quectel got a real fix through `gps-tool`, but that surfaced the stale-bytes/echo reader bug (fixed, see the `gps-integration` skill) plus a second, still-open issue (intermittent `AT+QGPSLOC=2` "no fix" despite a continuous NMEA lock) — the fix has not been redeployed to `dawn6g`'s running `gps-exporter` yet. `gps-tool.service`/`openwrt/gps-tool.init` are built/unit-tested but not installed anywhere — `gps-exporter` alone was deployed, since nothing needs the local-journalctl-only tool running continuously alongside it (see the `modem-tool`/`modem-exporter` redundancy note in `DEPLOYMENT.md`).

## License Constraint

GPL-2.0 — required for the eBPF program (`__license` section is "GPL"; kernel helpers demand it). Only applies to `bpf_src/tc_glitch.bpf.c` itself; every Go program that loads it (`dawn-agent`, `glitch/`, `glitch-tool`, `glitch-exporter`) does so via the ordinary syscall/netlink loading interface, not by linking against GPL code, so none of them are themselves bound by it — same as `modem/`, `modem-tool`, `modem-exporter`, `twamp/`, `twamp-tool`, `twamp-exporter`, `gps/`, `gps-tool`, `gps-exporter`, which have no such constraint at all.
