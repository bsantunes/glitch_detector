# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Hard Rules

- **Never call `mmcli --location-*` on `aaeon`, and never restart ModemManager there** — both have corrupted its QMI client state in the past (see the `gps-integration` skill's incident writeup).
- **Never re-enable the raw QMI GPS backend** (`gps.Supports(modem.MethodQMI)` / `NewQMISession`) — disabled after repeated production QMI-corruption incidents on `6global` and `aaeon` (see the `gps-integration` skill).
- **Never edit files directly in `~/glitch_detector` on `aaeon`** — that checkout only ever gets `git pull` (plus `commit`/`push`); develop elsewhere. **Release binaries: tag first, then build from a clean clone of the tag in `~/build/<tag>` on `aaeon`** (so every binary reports exactly that tag), cross-compiled for WaveOS (`DEPLOYMENT.md` step 3B).
- **`dawn6g` and `6global` are the priority boards** (both WaveOS, both live with SIM + antennas, all four exporters at `v2.3.4`). **`aaeon` is a build machine only** — no SIM, no antennas, can't gather modem data; its four exporters are to be stopped and disabled (binaries, the `/dev/dawn-gps` udev rule and the `gps-exporter` NMEA drop-in stay). Don't treat `aaeon`'s silence in InfluxDB as an incident. The ModemManager rules above still apply to it.
- **`bpf_src/test3_outage.sh`'s netem-induced outage is valid for `-capture ebpf` only** — AF_PACKET never sees the netem-dropped originals. Use `test3b_simultaneous.sh` to compare the two capture paths against each other.
- **Observation period on `dawn6g` and `6global`, restarted 2026-11-25 23:27:22 UTC** (when `dawn6g`'s `v2.3.4` upgrade finished; the previous `dawn6g`-only period ran from 2026-11-24 until then) — lab boards with no customer traffic, but their `gps_fix` rate per hour is being observed; config/binary changes on either wait until the user ends it. Read-only checks are fine.
- **Never send AT commands by hand on `ttyUSB9` while `uqmi-ubus` runs** on a WaveOS board — it holds that port (Quectel interface 02); replies go to whichever reader takes them first (see Known Issues).

## Project Overview

DAWN6G glitch detector: four shared Go packages (`modem/`, `twamp/`, `gps/`, `glitch/`), each with a `cmd/<x>-tool` (interactive diagnostic CLI, no InfluxDB) and a `cmd/<x>-exporter` (service that pushes to InfluxDB). Builds and runs only on Linux. `dawn-agent` (`main.go`) is the original single binary — **superseded and frozen, not built by default; its eBPF decode and TC attach handle are both stale, so don't trust its output** (`glitch-detector-internals` skill).

Gateway OS targets:
- **Debian** (`aaeon`): systemd units (`*.service`), ModemManager, SIMCom. The only place eBPF works.
- **WaveOS** (OpenWrt-based x86_64, `dawn6g`/`6global`): procd scripts in `openwrt/`. No `clsact`/TC-BPF in the kernel and no `tc` binary at all — so `glitch-exporter` runs there with `-capture afpacket`, and `bpf_src/test2_loss.sh` (netem) can't run (test1/test3/test3b don't need `tc`). No Go/clang/Python on-device: cross-compile with `GOOS=linux GOARCH=amd64 CGO_ENABLED=0` and copy the binary plus its init script (`MODEM_TOOL.md`'s WaveOS section).

## Repository gotchas

- `metrics-endpoint.md` is the authoritative InfluxDB/Grafana schema doc — read it before touching any exporter's schema. `DAWN6G Metrics Endpoint — Deployment Tutorial.docx` and `dawn6g-metrics/README.md` are superseded drafts with the wrong schema; don't follow them.
- `dawn6g-metrics/` is a reference copy of the server stack on `wservices.wavesys.pt` (`~/dawn6g-metrics` there), not something this repo deploys. `twampy-responder.service` is that server's TWAMP reflector unit, not a gateway unit.
- `DEPLOYMENT.md` is the runbook for adding a board. Exporter init scripts/units need `DEVICE_ID` and the token edited per board.
- `glitch-exporter.service` sets `Conflicts=dawn-agent.service` — both would attach eBPF to the same interface.

## Build & Run

`Makefile` targets: `make`, `make <x>-tool`, `make <x>-exporter`, `sudo make install-<x>`. Runtime flags: each `cmd/*/main.go`. eBPF (`glitch-tool`, `dawn-agent`) needs root.

- **On `aaeon`, build release binaries from a clean clone of the tag in `~/build/<tag>`** (tag first, then build), never from `~/glitch_detector` (deploy checkout, `git pull` only) or `~/glitch_detector_dev` (a stale non-git copy the old, now-retired `aaeon` services were built from). See also Hard Rules.
- **`go.mod`/`go.sum` are committed and pinned.** Never let dependencies change as a side effect of a build; update deliberately with `go get <module>@<version>` and commit the diff. (A fresh resolution once silently pulled `cilium/ebpf v0.22.0` and a `go1.26` toolchain on `aaeon`.)
- **Run `make embed` before `go vet ./...`/`go test ./...` on a fresh checkout** — `glitch/` embeds `glitch/tc_glitch.o` via `go:embed` and won't compile without it.
- The BPF program's own logic isn't covered by `go test`: validate with `bpf_src/verify_highest_ack_wraparound.sh` and live traffic (root + real hardware).

## Known Issues


- **`uqmi-ubus` on WaveOS** (from its Lua source in `/lib/wavesys/lib/lua/uqmi/` and `logread` on `dawn6g`):
  - Polls each modem every 10 s over AT (`uqmi.monitor.interval=10`); network scan (`AT+COPS=?`) disabled (`uqmi.scan.scan=0`). Quectel commands: `QENG="servingcell"`, `QSIMSTAT`, `QCCID`, `QUIMSLOT`, `CREG`, `COPS?`, `QTEMP`, `CBC`.
  - `modem_timeout()` opens the serial port per command with a 150 ms total limit and logs `Timeout waiting for OK response for command: ...` to syslog.
  - It holds `ttyUSB9` (Quectel if02); no `/dev/modem*` links exist. **Never send AT commands on `ttyUSB9` by hand while it runs** — replies go to whichever reader takes them first.
  - Observed timeouts: only `AT+QTEMP`, at 22:05:34, 22:10:20, 22:14:55, 22:19:31 on 2026-11-23 (every ~4m36s, strikingly regular). No `QENG` timeouts, so the signal data source is currently healthy.
  - **Poller-interference test (2026-11-23, three 30-min windows):** W1 all running — 3 QTEMP timeouts; W2 `gps-exporter` stopped — 6, every 4m56s (the most regular); W3 `modem-exporter` stopped — 3. Only `AT+QTEMP` ever timed out. Since they persist with either poller stopped, neither causes them; most likely QTEMP itself sometimes exceeds the daemon's 150 ms limit. Harmless: QTEMP's value isn't used, `QENG` never timed out, and `ubus` metrics never lagged more than one 10 s cycle over 90 min. The NMEA reader is not needed as a fix (stays parked).
  - The 2026-11-19 freeze began at 13:04, 12 min after a reboot and before any GPS work (14:16), so GPS likely didn't trigger it; its cause is still unknown.
- Other known issues live in the skills: the startup detection race, `uqmi-ubus.lua` discarding PCI/EARFCN/bandwidth, and `ubus` TAC/CellID not normalized → `modem-detection`; QMI LOC `endpoint hangup` corruption → `gps-integration` (and Hard Rules). Deployment state per board → `telemetry-schema`.
